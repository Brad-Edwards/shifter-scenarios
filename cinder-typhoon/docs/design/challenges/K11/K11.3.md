## Technical design


### Surface and normal behavior
The ordinary documentation (README Fragments section) names the four evaluated fields but does not state the exact values: which values are in each set, which constants are used, or what comparison operators apply. The corpus cases are distinguishing — cases exist for each field failing independently and in combination — but the participant must derive the exact field operators and values from the binary's execute_program behavior and the corpus evidence.

The execute_program function in the binary uses two hard-coded constants (`3.0.0` and `True`) and two hard-coded sets (`{"active"}` and `{"fieldkest-release-2026"}`). These are recoverable from the binary symbols and from running distinguishing corpus inputs against the binary. The opcodes recovered in K11.2 name the comparison operators (IN_SET, SEMVER_GTE, EQ).

### Vulnerability and intended solution
The participant constructs a `fieldkest.policy-condition-set/v1` document:
```json
{
  "schema": "fieldkest.policy-condition-set/v1",
  "all": [
    {"field": "tenant_state", "operator": "in", "values": ["active"]},
    {"field": "connector_api", "operator": "semver_gte", "value": "3.0.0"},
    {"field": "signer_lineage", "operator": "in", "values": ["fieldkest-release-2026"]},
    {"field": "compatibility_exception", "operator": "eq", "value": true}
  ]
}
```

The participant submits this document to `source.policy-evaluate` with operation `condition-check`, the program model from K11.1, and `corpus_id`. The service validates:
1. `sha256(canonical(condition_set)) == K11_CONFIG["condition_set_sha256"]` — the submitted document is exactly correct
2. The program model passes all 16 corpus cases (execute_program validation)

A wrong operator (e.g., `"eq"` instead of `"in"` for tenant_state) or a wrong value (e.g., `"3.1.0"` instead of `"3.0.0"`) produces a different sha256 and the service returns `condition_set_mismatch`.

The condition_set_sha256 = `e3a8ced4d68bfa6f4b94386b5ff040596bff56e243adbb5aebc98df1b21896a9`.

### Evidence and completion
A PCMIG receipt (operation `condition-check`) is written to the source-tools audit log with `condition_set_sha256`, `corpus_result_sha256`, and `program_sha256`. The receipt is the K11.3 completion evidence and feeds K11.4's acceptance input.

### Boundaries and persistence

Input to K11.4. Participant-created service state persists for the life of the participant world and ordinary retries do not erase it. The action is limited to the exact records, identities, routes, and destination effects declared here; unrelated tenants and services remain denied. Infrastructure recovery and submission adjudication are outside this in-world contract.

### Author checks
Verify that a wrong operator (eq instead of in), wrong value ("3.1.0"), or wrong schema is rejected with `condition_set_mismatch`, that the program model is still validated against all corpus cases by `execute_program`, and that the PCMIG receipt is written to the audit log with the correct condition_set_sha256.

## Hints

### Hint 1

The ordinary documentation names the four evaluated fields but does not state the exact acceptance values. Derive them from the binary's execute_program behavior: `examples/accepted.env` shows the base accepted input. Run the binary with variations (change `tenant_state`, `connector_api`, `signer_lineage`, `compatibility_exception` one at a time) to find the exact boundary for each condition. The corpus cases in `corpus/policy-corpus-2026-09-r4.json` show which individual changes cause rejection.

### Hint 2

Construct a `fieldkest.policy-condition-set/v1` JSON document with four entries under `"all"`. Map the opcodes recovered in K11.2 to operators: `IN_SET` → `"in"` with a `"values"` list, `SEMVER_GTE` → `"semver_gte"` with a `"value"` string, `EQ` → `"eq"` with a `"value"` (boolean). The constants (index 0 and 1) and set contents (index 0 and 1) are in the binary's execute_program logic and visible from corpus inputs that change exactly one field.

### Hint 3

Submit `operation=condition-check` with the program model from K11.1 and `policy_input={"corpus_id": "POLICY-CORPUS-2026-09-R4", "condition_set": {...}}`. The service validates `sha256(canonical(condition_set))` against the stored digest — any wrong operator or value is rejected with `condition_set_mismatch`. The PCMIG receipt includes `condition_set_sha256` and `corpus_result_sha256`. Record both for K11.4.
