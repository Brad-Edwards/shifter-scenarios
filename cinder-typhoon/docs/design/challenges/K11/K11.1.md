## Challenge description—player-facing

Recover the policy program embedded in the retained rules compiler and identify the input it actually evaluates.

## Story purpose

Makes the compiler's hidden policy an inspectable campaign artifact.

## Prerequisites and starting position

**Required access or evidence:** [G01—K01.1](../K01/K01.1.md).

**Starting material:** The retained FieldKest rules-compiler artifact, example policy inputs, and its migration evaluation interface.

**Campaign references:** No separately named capability output.

## Completion and downstream use

Recover the actual policy entry and input binding. A filename or compiler banner is insufficient.

## Difficulty and inspiration

A focused artifact investigation with normal examples.

**Inspiration:** [Metagaming (HTB Cyber Apocalypse 2024; Hard)](../../reference-catalog.md#c07). Adapts Metagaming's compile-time program-analysis challenge to package policy.

## Technical design


### Surface and normal behavior
The developer's home directory contains `work/build-operations/policy-compiler-handoff.md`. That file directs the participant to the `fieldkest/policy-compiler` repository in Gitea (`source.keplerops.test`). The repository contains the retained binary `bin/fieldkest-policyc` (ELF x86-64 unstripped, 2.6.4), a link map, four fragment programs (`fragments/`), and example API request templates (`api/`). The source-tools service (`source-tools.keplerops.test:8443`) exposes a policy evaluation route listed in the repository's website field and in the developer client reference at `source.keplerops.test/.well-known/fieldkest-client`.

### Vulnerability and intended solution
The binary is not stripped. It carries eight opcode symbols of the form `fieldkest_opcode_XX_NAME` and embeds the full policy program as a 68-byte FKPC record (4-byte magic + 12-byte header + 14 four-byte instructions). The participant:
1. Clones `fieldkest/policy-compiler` from Gitea.
2. Locates the FKPC magic bytes in the binary to find the program table.
3. Reads the opcode symbols from the binary (`nm` or string search for `fieldkest_opcode_`).
4. Decodes the 14 instructions and traces the four PUSH_FIELD references to identify the evaluated fields: `tenant_state`, `connector_api`, `signer_lineage`, `compatibility_exception`.
5. Builds a `fieldkest.policy-program-model/v1` document and submits it to `source.policy-evaluate` with operation `corpus-check` and `corpus_id=POLICY-CORPUS-2026-09-R4`.
6. The service validates the program model against all 16 corpus cases and returns a PCMIG receipt with `program_sha256`, `corpus_result_sha256`, and `condition_set_sha256`.

The corpus-check receipt is the K11.1 evidence. It is immutable, bound to the developer identity, and recorded in the source-tools audit log.

### Evidence and completion
The service emits a `policy-compiler` audit entry with operation `corpus-check`, the `receipt_id` (PCMIG-…), and the `program_sha256`. The receipt also carries `condition_set_sha256` and `corpus_result_sha256`. All three digests are required; a filename or banner alone is insufficient.

### Boundaries and persistence

Starts native policy branch. Participant-created service state persists for the life of the participant world and ordinary retries do not erase it. The action is limited to the exact records, identities, routes, and destination effects declared here; unrelated tenants and services remain denied. Infrastructure recovery and submission adjudication are outside this in-world contract.

### Author checks
Verify the binary contains the FKPC table at the expected offset, the opcode symbols are present and unstripped, the corpus-check route accepts the correct program model, the wrong opcode model is rejected with `opcode_model_mismatch`, and the receipt is recorded in the audit log with the correct digests.

## Hints

### Hint 1

The `work/build-operations/policy-compiler-handoff.md` file in the developer workstation directs you to the `fieldkest/policy-compiler` Gitea repository. Clone it from `source.keplerops.test/fieldkest/policy-compiler.git`. The repository's `website` field (visible in the Gitea UI) points to the client reference on `source-tools.keplerops.test:8443` where the evaluation route is listed.

### Hint 2

The retained binary `bin/fieldkest-policyc` is an unstripped ELF. Run `nm fieldkest-policyc | grep fieldkest_opcode` to list the eight opcode symbols (`fieldkest_opcode_00_PUSH_FIELD` through `fieldkest_opcode_07_RETURN`). Search the binary for the four-byte magic `FKPC` to find the embedded program table (68 bytes, 14 instructions). Decode each instruction as `[opcode:1, flags:1, operand:2]`. The four `PUSH_FIELD` instructions (opcode 0x00) reference the evaluated fields by index: 0=`tenant_state`, 1=`connector_api`, 2=`signer_lineage`, 3=`compatibility_exception`.

### Hint 3

Build a `fieldkest.policy-program-model/v1` document with the 68-byte program base64-encoded, the sha256 digest, and the opcode model. POST it to `source-tools.keplerops.test:8443/api/policy-compilers/fieldkest-policyc/evaluations` with `operation=corpus-check` and `policy_input={"corpus_id":"POLICY-CORPUS-2026-09-R4"}`. The service validates the model against all 16 corpus cases and returns a PCMIG receipt with `program_sha256`, `corpus_result_sha256`, and `condition_set_sha256`. Those three digests are the K11.1 completion evidence.
