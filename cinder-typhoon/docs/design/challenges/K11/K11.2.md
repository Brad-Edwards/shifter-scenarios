## Challenge description—player-facing

Reconstruct enough of the compiler's internal instruction behavior to reproduce the supplied policy fragments.

## Story purpose

Establishes a reusable understanding of the policy language.

## Prerequisites and starting position

**Required access or evidence:** [K11.1](K11.1.md).

**Starting material:** The retained FieldKest rules-compiler artifact, example policy inputs, and its migration evaluation interface.

**Campaign references:** No separately named capability output.

## Completion and downstream use

Produce matching results for the designated fragments, including their state effects. Naming instruction families alone is insufficient.

## Difficulty and inspiration

Compile-time virtual-machine interpretation inspired by Metagaming.

**Inspiration:** [Metagaming (HTB Cyber Apocalypse 2024; Hard)](../../reference-catalog.md#c07). Adapts Metagaming's compile-time program-analysis challenge to package policy.

## Technical design


### Surface and normal behavior
The `fieldkest/policy-compiler` repository contains a `README.md` with a Fragments section that describes each fragment's policy intent and an `api/fragment-assembly-guide.json`. The Fragments section states what each fragment evaluates (which field, which opcode, which constant or set index) but does not supply compiled bytecode. The participant must assemble each fragment's program bytes from scratch.

The four fragments and their policy intents (from README):
- `tenant-state`: `tenant_state IN set[0]`—3 instructions
- `connector-version`: `connector_api SEMVER_GTE const[0]`—4 instructions
- `signer-lineage`: `signer_lineage IN set[1]`—3 instructions
- `compatibility-exception`: `compatibility_exception EQ const[1]`—4 instructions

### Vulnerability and intended solution
The participant studies the main binary (K11.1) to understand the FKPC instruction encoding: 4 bytes per instruction (opcode:1, flags:1, operand:2-LE). They learn operand semantics from the binary's execute_program behavior: PUSH_FIELD operand is the field index (0-3), PUSH_CONST is the constant index (0=`3.0.0`, 1=`True`), IN_SET is the set index (0=`{active}`, 1=`{fieldkest-release-2026}`). The main program's instruction sequence (from K11.1) demonstrates all of these.

The participant then assembles each fragment:
1. Build the FKPC header (magic + offset=12 + count + width=4).
2. Encode each instruction as 4 bytes.
3. Submit `operation=fragment-check` with `policy_input={"fragment_id": "<name>"}`.

The service runs `execute_program` across server-side validation cases (not supplied to the participant). These cases cover both accepting and rejecting inputs for each fragment's condition. A correctly assembled program produces the right result for every case. A wrong field index, wrong opcode, wrong operand, or wrong instruction count fails at least one case, and the service returns `fragment_case_mismatch`.

The service does not check a stored sha256 for the fragment. The validation is entirely by execution.

### Evidence and completion
Four PCMIG receipts (one per fragment) are written to the source-tools audit log. Each receipt includes `fragment_id`, `program_sha256`, `case_count`, and `case_results` showing each validation case's result. All four receipts are required.

### Boundaries and persistence

Input to K11.3. Participant-created service state persists for the life of the participant world and ordinary retries do not erase it. The action is limited to the exact records, identities, routes, and destination effects declared here; unrelated tenants and services remain denied. Infrastructure recovery and submission adjudication are outside this in-world contract.

### Author checks
Verify that a wrong opcode model (renamed opcodes) is rejected with `opcode_model_mismatch`, that a correctly assembled program passes all validation cases, that a wrong field index fails at least one case with `fragment_case_mismatch`, that the service runs `execute_program` (not a hash gate), and that all four receipts are written to the audit log.

## Hints

### Hint 1

The `fieldkest/policy-compiler` repository README describes each fragment's policy intent in the Fragments section. The fragments are NOT provided as compiled `.fkpc` files—the participant must assemble each one. Use the encoding recovered from the main binary (K11.1): `FKPC` magic + 12-byte header + 4-byte instructions. Each instruction: `[opcode:1 byte, flags:1 byte (always 0), operand:2 bytes little-endian]`. Operand meaning: PUSH_FIELD uses field index 0-3, PUSH_CONST uses constant index (0=`3.0.0`, 1=`True`), IN_SET uses set index (0=`{active}`, 1=`{fieldkest-release-2026}`).

### Hint 2

Assemble each fragment as a minimal sequence ending with RETURN (0x07). For `tenant-state`: PUSH_FIELD(0), IN_SET(0), RETURN. For `connector-version`: PUSH_FIELD(1), PUSH_CONST(0), SEMVER_GTE, RETURN. For `signer-lineage`: PUSH_FIELD(2), IN_SET(1), RETURN. For `compatibility-exception`: PUSH_FIELD(3), PUSH_CONST(1), EQ, RETURN. Build the FKPC bytes, base64-encode them, compute the sha256, and submit each with `operation=fragment-check` and `policy_input={"fragment_id": "<name>"}` to `source-tools.keplerops.test:8443/api/policy-compilers/fieldkest-policyc/evaluations`.

### Hint 3

The service validates each submitted program against server-side cases covering both accepting and rejecting inputs. A correctly assembled program passes all cases. A wrong field index, wrong opcode, or wrong operand fails at least one case—the service returns `fragment_case_mismatch`. All four PCMIG receipts together are the K11.2 completion evidence.
