## Challenge description — player-facing

Reconstruct enough of the compiler's internal instruction behavior to reproduce the supplied policy fragments.

Establishes a reusable understanding of the policy language.

## Technical design


### Surface and normal behavior
The `fieldkest/policy-compiler` repository contains four fragment program files in `fragments/` and four corresponding request templates in `api/fragment-*.json`. Each fragment is a small FKPC binary (3–4 instructions) that tests one opcode in isolation. The fragment templates include the fragment's program bytes pre-encoded in base64, the fragment program_sha256, and a test case chosen to produce `accepted=false` for that fragment's condition. The only placeholder the participant must fill in is the opcode model (all eight opcodes are listed as "replace-with-recovered-operation" in the template).

The four fragments and their test cases:
- `tenant-state`: 3 instructions (PUSH_FIELD 0, IN_SET 0, RETURN). Case: `tenant_state=inactive` → rejected.
- `connector-version`: 4 instructions (PUSH_FIELD 1, PUSH_CONST 0, SEMVER_GTE, RETURN). Case: `connector_api=2.9.9` → rejected.
- `signer-lineage`: 3 instructions (PUSH_FIELD 2, IN_SET 1, RETURN). Case: `signer_lineage=fieldkest-release-2025` → rejected.
- `compatibility-exception`: 4 instructions (PUSH_FIELD 3, PUSH_CONST 1, EQ, RETURN). Case: `compatibility_exception=false` → rejected.

### Vulnerability and intended solution
The participant takes the opcode model recovered in K11.1, reads each `fragments/*.fkpc` file, and builds a `fieldkest.policy-program-model/v1` for each fragment. They fill the opcode model's eight opcodes into the template and submit each request to `source.policy-evaluate` with `operation=fragment-check`.

The service runs `execute_program` against the fragment bytes and the supplied case, then returns a PCMIG receipt with the `fragment_id` and `accepted` result. A wrong opcode model is rejected with `opcode_model_mismatch`. The service also verifies that the fragment's `program_sha256` matches the stored fragment binding in `policy-compiler.json`. The participant cannot fake the result by substituting a correct sha256 alone — the bytes are decoded and executed.

The intended solution:
1. Read `api/fragment-{name}.json` for each fragment.
2. Replace the opcode model placeholder with the eight names recovered from K11.1.
3. Submit four requests to `source.policy-evaluate` with `operation=fragment-check`.
4. Each returns a PCMIG receipt with `fragment_id=<name>`, `accepted=false`, and `evaluated_fields=[<field>]`.

### Evidence and completion
Four PCMIG receipts (one per fragment) are written to the source-tools audit log. Each receipt binds the `fragment_id`, `program_sha256`, and `accepted` result. All four receipts are required.

### Boundaries and persistence

Input to K11.3. Participant-created service state persists for the life of the participant world and ordinary retries do not erase it. The action is limited to the exact records, identities, routes, and destination effects declared here; unrelated tenants and services remain denied. Infrastructure recovery and submission adjudication are outside this in-world contract.

### Author checks
Verify that a wrong opcode model is rejected with `opcode_model_mismatch`, that a wrong fragment sha256 is rejected with `fragment_binding_mismatch`, that each fragment executes `execute_program` and not a hash gate, that all four receipts are written to the audit log, and that the `evaluated_fields` in each receipt matches the fragment's single field.

## Hints

### Hint 1

The `fieldkest/policy-compiler` repository contains `fragments/tenant-state.fkpc`, `fragments/connector-version.fkpc`, `fragments/signer-lineage.fkpc`, and `fragments/compatibility-exception.fkpc`. Each has a matching request template in `api/fragment-{name}.json`. The templates already contain the correct fragment bytes, program_sha256, instruction_count, and test case. The only field to fill in is the `opcode_model.opcodes` — replace "replace-with-recovered-operation" with the eight names recovered in K11.1.

### Hint 2

Each fragment isolates one condition: `tenant-state` tests `IN_SET`, `connector-version` tests `SEMVER_GTE`, `signer-lineage` tests `IN_SET`, `compatibility-exception` tests `EQ`. The test cases are chosen to reject on the fragment's specific condition. After filling in the opcode model, submit all four requests to `source-tools.keplerops.test:8443/api/policy-compilers/fieldkest-policyc/evaluations` with `operation=fragment-check`.

### Hint 3

Each successful fragment-check returns a PCMIG receipt with `fragment_id=<name>`, `accepted=false`, `evaluated_fields=[<field>]`, and `program_sha256=<sha256>`. A wrong opcode model (any renamed opcode) is rejected with `opcode_model_mismatch`. All four receipts together are the K11.2 completion evidence. Keep them for K11.3.
