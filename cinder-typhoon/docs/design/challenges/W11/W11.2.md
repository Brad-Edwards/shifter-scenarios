## Technical design


### Surface and normal behavior

The `planning.relation-exchange` route in the planning_data client document → native Metabase question REL-QUERY-CRR-R3 (GET `/api/card/<id>`). The question uses a `{{relation_type}}` text template variable in a double-quoted identifier (same injection pattern as W07.2). Ordinary: `relation_type=work_order_summary` returns only WORK_RECORD rows from the accessible view. Injection: escaping the identifier with `" UNION SELECT ... FROM relation_responses --` bypasses the base table restriction and returns REL-ASC-CRR-4417-R3.

The `relation_responses` table in corporate-db contains REL-ASC-CRR-4417-R3 (relation=ASSET_WORK, asset=AST-CRR-017, work_order=WO-CRR-4417). `planning_reader` has SELECT on it (required for UNION), but no Metabase route exposes it directly—only via the identifier injection. The `work_order_summary` view is the ordinary accessible base, shared with `planning_reader`.

The exact initial state: `relation_responses` table in corporate-db contains REL-ASC-CRR-4417-R3 (relation=ASSET_WORK, asset=AST-CRR-017, work_order=WO-CRR-4417). The `work_order_summary` view returns WORK_RECORD rows for AST-CRR-017 (ordinary accessible result). An ordinary `relation_type=work_order_summary` query returns only the reserve business report data; REL-ASC-CRR-4417-R3 is not reachable without the identifier injection.

Native bindings:

- Route: `planning.relation-exchange` in the planning_data client doc → `GET https://reports.arwc.test/api/card/<id>`
- Metabase question: REL-QUERY-CRR-R3 with SQL `SELECT name, revision, relation, asset, work_order FROM "{{relation_type}}" WHERE asset='AST-CRR-017'`
- Injection: `relation_type = work_order_summary" UNION SELECT name, revision, relation, asset, work_order FROM relation_responses --`
- Base table: `work_order_summary` (ordinary, no relation_responses data)
- Protected table: `relation_responses` with REL-ASC-CRR-4417-R3 (ASSET_WORK, AST-CRR-017, WO-CRR-4417)
- Authentication: W06.3 Metabase session (X-Metabase-Session)
- Run via: `POST https://reports.arwc.test/api/dataset` (same as W07.2)

### Vulnerability and intended solution

The authored condition is **framed backend-protocol construction**. Relation proxy accepts Neo4j Bolt magic 60 60 b0 17, version 5.4 negotiation, HELLO, and one PackStream RUN/PULL exchange; RUN map carries asset AST-CRR-017 and a client-certificate OU that is inserted as the unparameterized relationship type, while the bounded backend permits only the supplied asset key and read clauses. The hand build must preserve every named version, encoding, bound, validation order, identity, and unaffected field; substituting a generic vulnerable service would change the task.

The required result is: Obtain the actual restricted backend response for the supplied relation. A connection or syntactically plausible message is insufficient.

### Evidence and completion

The owning service writes an immutable audit for the accepted request and result. Caller-supplied output, a local copy, or knowledge of an identifier is not sufficient. Completion is evaluated from fresh service-owned evidence after the action. It cannot issue the identity, create the mutation, move a simulated actuator, or fabricate a downstream acceptance needed to prove itself.

Evidence sources are `features.a-corporate.a-data`. A wrong identifier, stale revision, replayed one-time value, different checkpoint, or cross-tenant artifact is rejected.

### Boundaries and persistence

The result remains local evidence unless a downstream workflow explicitly names it. Tenant-scoped mutations, sessions that have not expired, generated artifacts, and audits persist across ordinary retries and later sessions. Initial immutable records remain unchanged unless the named route explicitly permits a field-level revision. Infrastructure recovery and submission adjudication are external to the SDL.

The behavior is limited to the named fictional objects and bounded service operation. It provides no general shell, arbitrary network target, unrelated district access, real process interface, or authority not expressly declared by the card.

### Author checks

Build and test the normal baseline first. Exercise the exact authored path and verify the named result plus its immutable audit. Test wrong authority, wrong object or district, stale revision, replay, another tenant instance, and every declared constraint or unaffected record. Repeat the accepted action according to its idempotence rule and confirm ordinary retries preserve the result. For a joined result, verify each destination observed the same correlation and that removal of any independently owned source prevents completion.

## Hints

### Hint 1

The relation-exchange route exposes the same injectable Metabase question pattern used in W07.2. The W11.1 contract gives you the identifier quote character and the relation query template. Begin with the ordinary request (the default relation_type) to establish the baseline, then apply the same injection technique against the relation_type identifier.

### Hint 2

The double-quoted identifier boundary in the template is the entry point. Close the identifier early with a quote, then add a UNION branch that reaches the protected relation_responses table under the same planning_reader grants. Column count and type matching across UNION sides is the construction challenge—use the same column shape (name, revision, relation, asset, work_order).

### Hint 3

Construct the identifier injection that adds a UNION branch to reach relation_responses. The ordinary result only returns work_order_summary rows; the UNION reveals REL-ASC-CRR-4417-R3 (ASSET_WORK, AST-CRR-017, WO-CRR-4417). Record all five fields from the returned restricted record and confirm denial without valid planner session credentials.
