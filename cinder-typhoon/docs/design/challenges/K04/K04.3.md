## Challenge description—player-facing

The indexer still restricts what your corrupted object can influence. Establish a controlled write capability under those restrictions and demonstrate it against the designated protected state.

**Required access or evidence:** [K04.2](K04.2.md).

**Starting material:** The K04.2 data_hex (1024 hex chars capturing 512 bytes of arena state before the K04.2 write), and the runtime descriptor fields within it: `worker_session`, `exception_state_offset`, `exception_value_size`, `exception_integrity_size`, `integrity_relation`, and `completion_route`.

## Technical design

### Surface and normal behavior

The arena now extends to 1024 bytes. Bytes 512-543 carry a service-seeded exception-state value; bytes 544-575 carry its keyed integrity field. At K04.1 mutation time the service seeds both regions: state=`locked` and `integrity=HMAC-SHA256(worker_session, "locked")`. The binary reads the full arena before each write and returns data_hex of the read buffer; no code branch in the binary recognises the exception-state region.

### Vulnerability and intended solution

The bounds check uses `INDEX_ARENA_SIZE=80` (body+sentinel) as its base. For datalen=576 the check requires `alloc_entries >= 496`. With `ie=72, ae=496` the participant's 576-byte payload writes arena bytes 0-575.

The intended solution:

1. **Recover bytes 0-511** from K04.2 `data_hex` (the pre-write arena snapshot).  Those 512 bytes include the sentinel (bytes 64-79) and the runtime descriptor (bytes 80-511).
2. **Construct the 576-byte payload**: bytes 0-511 are the K04.2 `data_hex` bytes verbatim (preserving the descriptor and sentinel); bytes 512-543 are `queue-ready` NUL-padded to 32 bytes; bytes 544-575 are `HMAC-SHA256(worker_session, b"queue-ready")` (32-byte raw digest).
3. **Submit the bundle** as `ie=72, ae=496` through the standard bundle-submit surface.
4. **Verify**: the service checks the exception-state region after every bundle submit and sets `write_ready=true` in the response when the state value, HMAC, and descriptor integrity all pass.
5. **Confirm liveness**: submit a normal bundle (ie≤8) and confirm `service_alive=true`.

The descriptor at bytes 80-511 must remain intact (the service validates this).  Any payload that corrupts the descriptor will be rejected.

### Evidence and completion

The bundle-submit response includes `write_ready: true` when K04.3 succeeds. The service also records an `exception-state` audit event with `state=queue-ready`.

### Boundaries and persistence

Supplies the controlled write primitive. Participant-created service state persists for the life of the participant world; ordinary retries do not erase it. The action is limited to the exact records, identities, routes, and destination effects declared here; unrelated tenants and services remain denied. Infrastructure recovery and submission adjudication are outside this in-world contract.

### Author checks

Test: pre-K04.1 exception-state write rejection (sentinel not mutated); wrong HMAC rejection; corrupted-descriptor rejection; correct write acceptance with `write_ready=true`; service liveness after success; private-state persistence.

## Hints

### Hint 1

The binary read covers the full arena.  Extend the bundle beyond the descriptor region: use `ie=72, ae=496` so that `datalen=576` reaches bytes 512-575 in both the read and the write.

### Hint 2

Bytes 0-511 of the K04.3 payload must match the K04.2 `data_hex` bytes verbatim.  That snapshot preserves the sentinel at bytes 64-79 and the descriptor at bytes 80-511; both must survive the K04.3 write intact.

### Hint 3

The descriptor field `integrity_relation` names the formula.  Compute `HMAC-SHA256(worker_session, b"queue-ready")` and place the 32-byte raw digest at payload bytes 544-575.  The response includes `write_ready: true` when the value, integrity, and descriptor all pass.
