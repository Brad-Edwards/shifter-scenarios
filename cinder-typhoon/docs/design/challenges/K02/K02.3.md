## Challenge description — player-facing

Change the report produced by the test job while keeping the interface its caller expects. The support engineer should receive Cinder's version with a successful job result.

## Story purpose

Completes an early supply-chain episode in which a real support workflow accepts the operator's altered work as a successful report. A newcomer can see someone else's business process consuming their change.

## Prerequisites and starting position

**Required access or evidence:** ([K02.1](K02.1.md) AND [K02.2](K02.2.md)).

**Starting material:** The failing report job, a sample output, the fixture reference, and the developer's normal test interface.

**Campaign references:** No separately named capability output.

## Completion and downstream use

Produce a fresh altered report accepted by the test interface. Its content and job binding must agree; an edited local file or green status alone is insufficient.

The conclusion shows the report as received in the support handover, with the operator's changed result alongside the successful job status and preserved ordinary fields. It uses the report already produced by the service task; there is no extra delivery step or accepted result. This is the first small example of a reassuring status accompanying a compromised result, a theme that returns at ARWC.

## Difficulty and inspiration

Requires preserving ordinary behavior while composing the recovered fixture and earned import capability.

**Inspiration:** Original challenge for this campaign.

## Technical design


### Surface and normal behavior
An isolated Jenkins or Woodpecker test consumer invokes the FieldKest report interface with the recovered fixture and publishes the resulting support handover report.

### Vulnerability and intended solution
The test input permits a compatible report implementation selected through its documented extension point. The intended solution combines the fixture baseline and importer contract to produce changed content while preserving required interface fields.

### Evidence and completion
Completion is a green job whose fresh report has the expected baseline fields and operator change; the support handover displays that actual output and the job receipt binds it.

### Boundaries and persistence

First changed-but-green result Participant-created service state persists for the life of the participant world and ordinary retries do not erase it. The action is limited to the exact records, identities, routes, and destination effects declared here; unrelated tenants and services remain denied. Infrastructure recovery and submission adjudication are outside this in-world contract.

### Author checks
Test baseline green behavior, interface-breaking failure, intended compatible changed report, handover receipt correlation, no accepted result for a local edit.
