## Challenge description—player-facing

Construct input that causes the inspection components to disagree about the request they are processing. Demonstrate the disagreement with a controlled downstream effect.

## Story purpose

Turns boundary analysis into an exploitable request capability.

## Prerequisites and starting position

**Required access or evidence:** [K07.1](K07.1.md).

**Campaign references:** No separately named capability output.

## Completion and downstream use

Produce a fresh, reproducible downstream action inconsistent with the front-end request interpretation. A malformed response or rejected request is insufficient.

## Technical design


### Surface and normal behavior
The inspector and assessment component parse a compact request envelope before producing a bounded test assessment.

### Vulnerability and intended solution

The inspection service (front end, registry.py on :9000) and the upstream assessor (Python BaseHTTPRequestHandler on :9001) are two distinct real components that communicate over a persistent HTTP/1.1 keep-alive connection. They disagree on request framing at two layers:

**Name framing**: The front end decodes the envelope name field as raw UTF-8 bytes; the assessor applies NFKC normalization + casefold + `[:name_length]` truncation to the same bytes. A KELVIN SIGN (U+212A, 3 bytes = 1 char) produces:
- Front: `front_name = "K"` (1 char, raw 3-byte Kelvin)
- Assessor: `assessor_name = "k\x00\x0a"` (3 chars—Kelvin normalized to 'k' + next 2 bytes of the following_length field)

**Body framing** (the HTTP smuggling boundary): The inspection service sets `Content-Length = front_following_length` (from the envelope header) when forwarding to the assessor. If `front_following_length` = 10 (just the 10-byte header) but the actual forwarded body is 130 bytes, the assessor reads only 10 bytes; the remaining 120 bytes stay in the persistent HTTP/1.1 socket and become the prefix of the NEXT request on the same keep-alive connection.

The intended solution crafts a binary envelope where:
1. `front_following_length = 10` (CL to assessor = exactly the header size: FKI1 + name_len + Kelvin + following_len = 10 bytes)
2. After the first 10 bytes: a valid HTTP POST to `/assess/privileged` (the protected route), with its 3-byte body as the envelope payload bytes
3. Total envelope = 130 bytes; CL to assessor = 10

The participant submits via persistent HTTP/1.1 to Nginx:
1. Envelope request → inspection service → assessor: CL=10, body=130 bytes; assessor reads 10 bytes → returns normal result; 120 bytes stay in socket
2. Next inspection request on the SAME connection → inspection service → assessor on the SAME persistent connection: inspection service sends POST /assess, but reads the PREVIOUSLY BUFFERED privileged response (sent by the assessor after processing the smuggled POST)
3. The inspection result contains `"assessment": "privileged-access-confirmed"`—the protected action's output delivered through the smuggled connection

### Evidence and completion
Both component audit records, with their distinct interpreted request IDs and the expected compatibility-assessment effect, form completion evidence.

### Boundaries and persistence

Parser-confusion primitive Participant-created service state persists for the life of the participant world and ordinary retries do not erase it. The action is limited to the exact records, identities, routes, and destination effects declared here; unrelated tenants and services remain denied. Infrastructure recovery and submission adjudication are outside this in-world contract.

## Hints

### Hint 1

The binary envelope format is `FKI1 + name_length(1) + name(name_length bytes) + front_following_length(2 big-endian) + ...`. The inspection service sets `Content-Length = front_following_length` when forwarding to the assessor. The assessor (Python BaseHTTPRequestHandler) reads exactly Content-Length bytes; surplus bytes stay in the persistent HTTP/1.1 socket. Use `front_following_length = 10` to make the assessor read only the 10-byte header and leave the rest.

### Hint 2

After the envelope bytes, include a valid HTTP POST to a protected assessor route as the surplus body. Set `front_following_length = 10` (the header size: FKI1(4) + name_len(1) + Kelvin(3) + following_len(2) = 10). The smuggled POST body fits in the 3 "payload" bytes at the end of the envelope. Use KELVIN SIGN U+212A as the name (3 bytes, 1 char) to prove the name framing disagreement in the result.

### Hint 3

Submit the crafted envelope, then immediately send a normal inspection request on the SAME HTTP/1.1 keep-alive connection to the delivery service. The inspection service reads the assessor's response to the SMUGGLED request (buffered in the persistent socket) instead of the expected normal assessment. The inspection result contains the protected route's data—the downstream controlled effect.
