## Challenge description — player-facing

Construct input that causes the inspection components to disagree about the request they are processing. Demonstrate the disagreement with a controlled downstream effect.

## Technical design


### Surface and normal behavior
The inspector and assessment component parse a compact request envelope before producing a bounded test assessment.

### Vulnerability and intended solution

The inspection service (front end) and the upstream assessor (back end) parse the compact envelope name field differently:

- **Front end** reads `name_length` (data[4]) BYTES from position 5: `front_raw = data[5:5+name_length]`. It decodes those bytes directly as UTF-8 — `front_name = front_raw.decode("utf-8")`.
- **Back end (assessor)** reads `data[5:-3]` as UTF-8, applies NFKC normalization + Unicode casefold, then truncates to `name_length` CHARACTERS: `assessor_name = normalize(casefold(assessor_buffer))[:name_length]`.

The deliberate boundary: `inspection-compat.fki` contains a KELVIN SIGN (U+212A, 3 UTF-8 bytes = `\xe2\x84\xaa`) as the name. The 3 bytes decode to a single character "K", but NFKC-normalizing the buffer produces "kqa" (Kelvin→k, then the two following bytes "qa"). Since `name_length = 3`:

- Front: `front_name = "K"` (1 char — raw 3-byte Kelvin sign)
- Assessor: `assessor_name = "kqa"` (3 chars — normalized+casefolded)

The check (`assessor_name == "kqa"`) passes, but the two components record different request IDs. The participant submits the fixture to `packages.inspection-envelope` as `Content-Type: application/octet-stream`. The endpoint validates that sha256(submitted) matches the `compatibility_envelope_sha256` from the K07.1 trace (the fixture sha256 matches because it was seeded from the same file). The result shows `front_end.request_id = "K"` and `assessor.request_id = "kqa"` — the proven parser disagreement.

### Evidence and completion
Both component audit records, with their distinct interpreted request IDs and the expected compatibility-assessment effect, form completion evidence.

### Boundaries and persistence

Parser-confusion primitive Participant-created service state persists for the life of the participant world and ordinary retries do not erase it. The action is limited to the exact records, identities, routes, and destination effects declared here; unrelated tenants and services remain denied. Infrastructure recovery and submission adjudication are outside this in-world contract.

### Author checks
Test ordinary agreement, intended parser disagreement, invalid envelope rejection, sentinel-only effect, both audit records.

The developer workstation has `work/registry/inspection-compat.fki`. Inspect its bytes: it starts with `FKI1`, then a name_length byte, then 3 bytes that are NOT plain ASCII. Decode those 3 bytes as UTF-8 and compare the character with its NFKC-normalized + casefolded form to identify the boundary.
