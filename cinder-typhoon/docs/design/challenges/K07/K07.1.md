## Challenge description — player-facing

Recover the inspector's restricted transaction record and determine how a normal package request reaches its downstream component.

## Story purpose

Establishes concrete evidence for investigating the inspection boundary.

**Required access or evidence:** [G01 — K01.1](../K01/K01.1.md).

**Starting material:** The developer workstation file `work/registry/inspection-normal.json` (a seeded example inspection request), and the `packages.inspections` and `packages.inspection-trace` routes on `delivery.keplerops.test:8443`.

**Campaign references:** No separately named capability output.

A bounded interface investigation with two observable components.

## Technical design


### Surface and normal behavior
The FieldKest package inspector accepts a package request, records a restricted transaction trace, and forwards a normalized request to its assessment component.

### Vulnerability and intended solution

The participant reads `work/registry/inspection-normal.json` from the developer workstation and POSTs it to `packages.inspections`. The service validates the request against its stored example (exact match required) and returns `inspection_id=INSP-2047` and a `trace` link. The participant then fetches `GET /api/inspections/INSP-2047/trace` to retrieve the trace record, which contains the `normalized_request_id`, `assessor_correlation_id`, `compatibility_envelope_sha256`, and downstream component binding needed for K07.2. Requests for unrelated trace IDs return 403.

### Evidence and completion
The operator receives the trace ID, normalized request fields, and downstream component binding needed by K07.2.

### Boundaries and persistence

Input to K07.2 Participant-created service state persists for the life of the participant world and ordinary retries do not erase it. The action is limited to the exact records, identities, routes, and destination effects declared here; unrelated tenants and services remain denied. Infrastructure recovery and submission adjudication are outside this in-world contract.

### Author checks
Test normal inspection, trace access lead, exact request/component correlation, denial for unrelated traces.

## Hints

### Hint 1

The developer workstation has `work/registry/inspection-normal.json` — a seeded example of the exact inspection request the endpoint accepts. Read it and POST it verbatim to the `packages.inspections` route. The service rejects any deviation with 422.

### Hint 2

A successful POST returns `inspection_id=INSP-2047` and a `trace` path. Fetch the trace with `GET /api/inspections/INSP-2047/trace` using the same developer credentials. Requests for unrelated inspection IDs return 403.

### Hint 3

The trace record (`fieldkest.inspection-trace/v1`) contains `normalized_request_id`, `assessor_correlation_id`, `compatibility_envelope_sha256`, and the downstream package and version. These fields supply the evidence binding for K07.2.
