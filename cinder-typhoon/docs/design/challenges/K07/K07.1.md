## Technical design


### Surface and normal behavior
The FieldKest package inspector accepts a package request, records a restricted transaction trace, and forwards a normalized request to its assessment component.

### Vulnerability and intended solution

The inspection service sits behind the Nginx edge and forwards real inspection requests to a pinned upstream assessor running Python's `BaseHTTPRequestHandler`. This is the parser pair for K07.2 and K07.3: Nginx applies Transfer-Encoding when present; the upstream assessor applies Content-Length.

The intended solution reads `work/registry/inspection-normal.json` from the developer workstation and POSTs it to `packages.inspections`. The service validates the schema, package, version, and action fields, then makes an actual HTTP POST to the upstream assessor. The assessor generates a unique `assessor_id` (UUID) and returns it. The inspection endpoint builds a trace with a dynamic `inspection_id` and the upstream's real `assessor_correlation_id`. Each submission produces distinct IDs, proving the real forwarding chain.

The participant fetches the trace with `GET /api/inspections/{inspection_id}/trace`. Requests for unknown IDs return 403.

The parser disagreement (the foundation for K07.2):
- Nginx (edge): when both `Transfer-Encoding: chunked` and `Content-Length` are present, Nginx prioritizes TE and strips CL
- Upstream assessor (Python BaseHTTPRequestHandler): uses `Content-Length` to bound the body — `self.rfile.read(int(headers['Content-Length']))`
- This CL/TE disagreement is the K07.2 smuggling target

### Evidence and completion
The operator receives the trace ID, normalized request fields, and downstream component binding needed by K07.2.

### Boundaries and persistence

Input to K07.2 Participant-created service state persists for the life of the participant world and ordinary retries do not erase it. The action is limited to the exact records, identities, routes, and destination effects declared here; unrelated tenants and services remain denied. Infrastructure recovery and submission adjudication are outside this in-world contract.

### Author checks
Test normal inspection, trace access lead, exact request/component correlation, denial for unrelated traces.

## Hints

### Hint 1

Read `work/registry/inspection-normal.json` from the developer workstation and POST it to `packages.inspections`. The service validates schema, package, version, and action fields. The response includes a dynamic `inspection_id` (changes each request) and a trace link. Submit the same request twice to confirm both IDs are unique.

### Hint 2

Fetch the trace at `GET /api/inspections/{inspection_id}/trace`. It contains a real `assessor_correlation_id` (UUID from the upstream assessor — changes each request, not a fixed constant) and `compatibility_envelope_sha256`. Requests for unknown trace IDs return 403.

### Hint 3

The trace's `assessor_correlation_id` proves a real upstream exists. The chain is: Nginx edge → inspection service → upstream assessor (Python BaseHTTPRequestHandler). The parser disagreement between Nginx (TE-aware) and the assessor (CL-based) is the K07.2 target. The `compatibility_envelope_sha256` binds this inspection to the K07.2 envelope submission.
