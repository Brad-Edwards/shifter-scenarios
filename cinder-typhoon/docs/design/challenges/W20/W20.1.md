## Technical design


### Surface and normal behavior

`a-instruments` and its `independent-instruments` application own this card. The participant:
1. Calls `GET https://independent-instruments.arwc.test/api/firmware-images/current` with CORPORATE Bearer token
2. Receives the image manifest (sha256, record layout) and the image base64
3. Parses the 8192-byte image into 64-byte records using the declared layout
4. Finds the inspection record using `logical_flash()` (highest-sequence wins)
5. Submits the parsed record to `POST /api/maintenance-records/current`

**Flash record layout** (from the manifest, also in process_services.py):
- Bytes 0–3: magic (`F204`)
- Bytes 4–7: sequence (uint32 LE)
- Bytes 8–9: payload_length (uint16 LE, max 44)
- Byte 10: status (1=REVIEW, 2=ACCEPTED)
- Byte 11: status_bits
- Bytes 12–55: payload (`record_id\0asset\0inspection_date` null-separated)
- Bytes 56–59: CRC32C of bytes 0–55 (uint32 LE)
- Bytes 60–62: `\xff\xff\xff` (reserved)
- Byte 63: commit byte (`0x00`)

**Image records** (parsed from IMG-FIT-204-R6.bin, 8192 bytes, sha256=f2bf5efd...):
- Offset 0: `CAL-FIT-204-R7` / FIT-CRR-204A / 2026-08-19 / seq=91 / ACCEPTED
- Offset 64: `INSP-FIT-204-118` / FIT-CRR-204B / 2026-09-18 / seq=118 / REVIEW (target)

**Gradeable answer**: sha256 and all 7 fields of INSP-FIT-204-118. The image is also in Gitea (`clara.morivelle/retained-engineering-tools/instruments/IMG-FIT-204-R6.bin`). None of the gradeable field values are readable from any shipped file — the participant must parse the binary.

**Fresh-evidence grading**: The service sets `inspection_recovered=True` and writes `maintenance-record-created` audit. Only a correctly parsed submission passes.

Native bindings:
- `a-control.a-instruments/process-view:independent-instruments.arwc.test/api/firmware-images/current` (GET, sets flash_observed)
- `a-control.a-instruments/process-view:independent-instruments.arwc.test/api/maintenance-records/current` (POST, validates)
- `a-control.a-instruments/gitea:clara.morivelle/retained-engineering-tools/instruments/IMG-FIT-204-R6.bin`

The private service-loader contract is `content.arwc-a-instruments.w20-1-what-the-image-kept`.

### Vulnerability and intended solution

This is a flash image parsing and record extraction task. The participant must implement the 64-byte record format, apply CRC32C validation, use logical_flash (highest sequence per record_id), and supply all 8 fields (image_sha256, record_id, asset, inspection_date, sequence, status, status_bits, crc32c, offset) to the service. The service validates every field.

The required result is: Recover the actual record-bearing data and image binding. No physical kit is required.

### Evidence and completion

The owning service writes an immutable audit for the accepted request and result. Caller-supplied output, a local copy, or knowledge of an identifier is not sufficient. Completion is evaluated from fresh service-owned evidence after the action. It cannot issue the identity, create the mutation, move a simulated actuator, or fabricate a downstream acceptance needed to prove itself.

Evidence sources are `features.a-control.a-instruments`. A wrong identifier, stale revision, replayed one-time value, different checkpoint, or cross-tenant artifact is rejected.

### Boundaries and persistence

The result remains local evidence unless a downstream workflow explicitly names it. Tenant-scoped mutations, sessions that have not expired, generated artifacts, and audits persist across ordinary retries and later sessions. Initial immutable records remain unchanged unless the named route explicitly permits a field-level revision. Infrastructure recovery and submission adjudication are external to the SDL.

The behavior is limited to the named fictional objects and bounded service operation. It provides no general shell, arbitrary network target, unrelated district access, real process interface, or authority not expressly declared by the card.

### Author checks

Build and test the normal baseline first. Exercise the exact authored path and verify the named result plus its immutable audit. Test wrong authority, wrong object or district, stale revision, replay, another tenant instance, and every declared constraint or unaffected record. Repeat the accepted action according to its idempotence rule and confirm ordinary retries preserve the result. For a joined result, verify each destination observed the same correlation and that removal of any independently owned source prevents completion.

## Hints

### Hint 1

Call `GET https://independent-instruments.arwc.test/api/firmware-images/current` with your CORPORATE Bearer token. The response includes the image manifest (sha256, erase_page_bytes=4096, record_bytes=64, record_layout) and the image base64. The manifest sha256 is the `image_sha256` for the POST. The image is also in Gitea (`clara.morivelle/retained-engineering-tools/instruments/IMG-FIT-204-R6.bin`).

### Hint 2

Parse the 8192-byte image into 128 × 64-byte records. Each valid record starts with magic `F204`, ends with commit byte `0x00`, has CRC32C of bytes 0–55 at bytes 56–59, and contains null-separated `record_id\0asset\0inspection_date` at bytes 12+. Status at byte 10 (1=REVIEW, 2=ACCEPTED) and status_bits at byte 11. When multiple records share a record_id, the one with the highest sequence (uint32 LE at bytes 4–7) is the logical record.

### Hint 3

Submit `POST https://independent-instruments.arwc.test/api/maintenance-records/current` with CORPORATE Bearer: `{image_sha256, record_id, asset, inspection_date, sequence, status, status_bits, crc32c, offset}` for the target inspection record. The service validates all 8 record fields plus the image_sha256. Success returns the inspection record with fresh audit evidence and sets inspection_recovered=True for W20.2.
