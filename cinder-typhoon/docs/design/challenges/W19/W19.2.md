## Technical design


### Surface and normal behavior

`a-engineering` and its engineering workbench own this card. The participant analyzes the binary's 32-bit compatibility decoder (the `mixed_mode_entry` path), implements the decoder correctly, and submits the reproduced result to the service.

**Binary structure** (`diag-crr-mixed-19`, from `clara.morivelle/retained-engineering-tools`):
- `_start` → `decoder64`: x86-64 long-mode entry, same rolling decoder in 64-bit context
- `mixed_mode_entry`: pushes CS=0x23 (32-bit compat selector) + return address, then `RETFQ` into 32-bit mode
- In 32-bit mode: `eax`, `ecx` are 32-bit; XOR, ROL, ADD all wrap at 32 bits

**Alternate test record** (embedded in the binary, visible via strings): `WRAP-FFFFFFFF-OG2`

**Correct 32-bit decoder** (rolling32 algorithm):
```python
value = 0x6D2B79F5
for byte in record.encode("ascii"):
    value = (rotl32(value ^ byte, 5) + 0x9E3779B9) & 0xFFFFFFFF
```
where `rotl32(v, n) = ((v << n) | (v >> (32 - n))) & 0xFFFFFFFF`

**Service route**: `POST https://process-view.arwc.test/api/signature-records/current/interpretation`
- Requires W19.1 (`diagnostic_observed = True`)
- Body: `{"record": "WRAP-FFFFFFFF-OG2", "rolling32": "<8-hex-digits>"}`
- Validates: supplied rolling32 == correct 32-bit decoder result
- Success: returns `DIAG-TRACE-COMPAT-19`, sets `compatibility_reproduced = True`

**Fresh-evidence grading**: The service validates the submitted rolling32 against the computed value. A wrong rolling32 (e.g., from 64-bit emulation without 32-bit wrap) is rejected with 409. The state flag and audit confirm the correct decoder was implemented.

### Vulnerability and intended solution

The authored condition is **mixed x86-64 and i386 execution semantics**. The ELF enters x86-64, then uses RETFQ with selector 0x23 to enter 32-bit compatibility mode for the actual decoder. Decoder registers and address arithmetic wrap at 32 bits. Emulating the decoder as 64-bit arithmetic (without MASK32) produces a different rolling value and is rejected.

The required result is: Produce the correct alternate-path result for the supplied input. Naming an execution mode without recovering behavior is insufficient.

## Hints

### Hint 1

The binary has two entry points. The ordinary W19.1 traces use `_start` → `decoder64` (long mode). The alternate path uses `mixed_mode_entry` which pushes CS=0x23 (32-bit compatibility segment) and executes RETFQ to switch modes. Run `objdump -M intel -d` and look for the far return and the 32-bit code section. The alternate test record `WRAP-FFFFFFFF-OG2` is embedded in the binary (visible via strings).

### Hint 2

Implement the 32-bit decoder: `value = (rotl32(value ^ byte, 5) + 0x9E3779B9) & 0xFFFFFFFF`, starting from `0x6D2B79F5`. The 32-bit rotate is `((v << 5) | (v >> 27)) & 0xFFFFFFFF`. All intermediate values wrap at 32 bits. Applying this to `WRAP-FFFFFFFF-OG2` gives an 8-hex-digit result. Applying it as 64-bit arithmetic (skipping the masks) gives a different result that the service rejects.
