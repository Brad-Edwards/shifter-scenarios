## Technical design


### Surface and normal behavior

The retained engineering diagnostic is delivered via Gitea as part of `clara.morivelle/retained-engineering-tools`. The participant downloads the binary, performs offline analysis to recover the project-family binding, and validates against the live OT system.

**Gitea location** (`engineering.arwc.test`, read-only with engineering identity):
- Repo: `clara.morivelle/retained-engineering-tools`
- Path: `engineering/diag-crr-mixed-19`
- SHA-256: `55955633e4031a8e67019593e09f108c8d026d1b603f27ae3b19ddf9c72d4117`
- Format: linux x86_64 ELF, statically linked, stripped (no debug symbols)
- Companion: `engineering/replay-crr-r19` (R19 replay tool, same project family)

**Mixed-execution-mode analysis** (the RE challenge):
The binary contains both 64-bit (decoder64) and 32-bit (mixed_mode_entry) code sections. The 64-bit entry path runs the rolling decoder over embedded data. The 32-bit path uses a long-return instruction to transition execution modes. This is the Gateway-style mixed-mode analysis.

**Live OT validation** (after recovering the project family from binary analysis):
- OPC UA: `CRR.ProjectRevision = 364` (nsu=urn:arwc:crr:tags;s=CRR.ProjectRevision)
- Gitea: `clara.morivelle/cairn-reach-outlet-control` (current OpenPLC project)
- Historian: `ot_history.tag_catalog.variable = 'ProjectRevision'`
- The binary belongs to a different revision than the running system — the diagnostic was retained from an earlier project generation without being updated.

Native bindings:
- `a-engineering.a-engineering/gitea:clara.morivelle/retained-engineering-tools/engineering/diag-crr-mixed-19`
- `a-engineering.a-hmi/OPC-UA:nsu=urn:arwc:crr:tags;s=CRR.ProjectRevision`
- `a-engineering.a-historian/PostgreSQL:ot_history.tag_catalog`

### Vulnerability and intended solution

The participant must:
1. Locate the binary in Gitea (`clara.morivelle/retained-engineering-tools`)
2. Verify SHA-256 to confirm it is the authentic retained artifact
3. Perform offline static and dynamic analysis to recover the embedded project identifier
4. Identify the project-family binding from that identifier
5. Validate the recovered binding against the live OT system (ProjectRevision OPC UA + historian)

The binary contains a recoverable identifier string that reveals the project family. The mismatch between the recovered project generation and the running system's ProjectRevision is the discovery.

The required result is: Recover the correct diagnostic and project-family binding. K28 can help locate it but is not a prerequisite.

### Hint 3

After recovering the project identifier from the binary, check the live OT: query `CRR.ProjectRevision` from the OPC UA browser or the historian (`ot_history.tag_catalog`) and compare with the recovered project generation. The gap between the two confirms why the diagnostic was never retired.
