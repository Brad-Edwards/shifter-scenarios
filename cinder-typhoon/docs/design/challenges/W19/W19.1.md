## Challenge description — player-facing

Recover the retained engineering diagnostic associated with the outlet records and identify its actual project family.

## Story purpose

Opens an optional reverse-engineering route through product history.

## Prerequisites and starting position

**Required access or evidence:** [OT_READ](../../capability-routes.json).

**Starting material:** The retained engineering diagnostic, ordinary examples, and the current read-only observation context. K28's note is an optional discovery lead.

**Campaign references:** No separately named capability output.

## Completion and downstream use

Recover the correct diagnostic and project-family binding. K28 can help locate it but is not a prerequisite.

## Difficulty and inspiration

A bounded artifact and provenance investigation.

**Inspiration:** [Gateway (HTB Cyber Apocalypse 2025; Hard)](../../reference-catalog.md#c21). Adapts Gateway's mixed-execution-mode analysis; it is a different problem from K28's loader investigation.

## Technical design


### Surface and normal behavior

The retained engineering diagnostic is delivered via Gitea as part of `clara.morivelle/retained-engineering-tools`. The participant downloads the binary, performs offline analysis to recover the project-family binding, and validates against the live OT system.

**Gitea location** (`engineering.arwc.test`, read-only with engineering identity):
- Repo: `clara.morivelle/retained-engineering-tools`
- Path: `engineering/diag-crr-mixed-19`
- SHA-256: `55955633e4031a8e67019593e09f108c8d026d1b603f27ae3b19ddf9c72d4117`
- Format: linux x86_64 ELF, statically linked, stripped (no debug symbols)
- Companion: `engineering/replay-crr-r19` (R19 replay tool, same project family)

**Participant path (authenticated service call):**

The participant earns the CORPORATE session via the FieldLink handover (W01). They then:
1. Discover the `process.diagnostic-program` route in the published client reference.
2. Download `diag-crr-mixed-19` from Gitea to have the binary for offline analysis (W19.2–W19.4).
3. Call `GET https://process-view.arwc.test/api/diagnostic-programs/current` with the CORPORATE Bearer token.
4. The service returns the authoritative record: `record_id=DIAG-CRR-MIXED-19`, `project_family=CRR-CTRL-R19`, `format=ELF64-x86-64-stripped`, sha256, and ordinary_traces (the w19_verifier values for the R19 test records).
5. Compare `project_family` with the live system: `CRR.ProjectRevision = 364` (the running system belongs to a later generation, CRR-CTRL-R21 → R364). The mismatch is the finding.

**Fresh-evidence grading:**
The service sets `diagnostic_observed = True` in its state and writes an immutable `legacy-diagnostic-read` audit. Completion is verified from the state flag and the audit — not from the companion binary or any participant-supplied string. Submitting the plaintext `project_family` without calling the endpoint does not complete the card.

**Live OT validation:**
- OPC UA: `CRR.ProjectRevision = 364` (nsu=urn:arwc:crr:tags;s=CRR.ProjectRevision)
- Historian: `ot_history.tag_catalog.variable = 'ProjectRevision'` (series=project_revision)

Native bindings:
- `a-engineering.a-engineering/process-view:process-view.arwc.test/api/diagnostic-programs/current`
- `a-engineering.a-engineering/gitea:clara.morivelle/retained-engineering-tools/engineering/diag-crr-mixed-19`
- `a-engineering.a-hmi/OPC-UA:nsu=urn:arwc:crr:tags;s=CRR.ProjectRevision`

### Vulnerability and intended solution

The participant authenticates with their earned CORPORATE session and calls the diagnostic endpoint. The service returns the authoritative diagnostic record (record_id, project_family, sha256, ordinary_traces). The participant reads the returned `project_family` and compares it to the live OT's `ProjectRevision`. The gap between the diagnostic's project generation and the running system is the finding. The service call and its audit are the evidence; a plaintext lookup does not substitute.

The companion binary and the Gitea download are starting material for W19.2–W19.4 (mixed-mode analysis of the binary itself); they are not the W19.1 answer path.

The required result is: Recover the correct diagnostic and project-family binding. K28 can help locate it but is not a prerequisite.

### Evidence and completion

The owning service writes an immutable audit for the accepted request and result. Caller-supplied output, a local copy, or knowledge of an identifier is not sufficient. Completion is evaluated from fresh service-owned evidence after the action. It cannot issue the identity, create the mutation, move a simulated actuator, or fabricate a downstream acceptance needed to prove itself.

Evidence sources are `features.a-engineering.a-engineering`. A wrong identifier, stale revision, replayed one-time value, different checkpoint, or cross-tenant artifact is rejected.

### Boundaries and persistence

The result remains local evidence unless a downstream workflow explicitly names it. Tenant-scoped mutations, sessions that have not expired, generated artifacts, and audits persist across ordinary retries and later sessions. Initial immutable records remain unchanged unless the named route explicitly permits a field-level revision. Infrastructure recovery and submission adjudication are external to the SDL.

The behavior is limited to the named fictional objects and bounded service operation. It provides no general shell, arbitrary network target, unrelated district access, real process interface, or authority not expressly declared by the card.
