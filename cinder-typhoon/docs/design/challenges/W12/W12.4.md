## Challenge description—player-facing

Reconstruct the surviving collection relationship and obtain the current protected data associated with the archived maintenance identity.

## Story purpose

Makes old intelligence useful without substituting it for current plant observations.

## Prerequisites and starting position

**Required access or evidence:** [W12.3](W12.3.md).

**Starting material:** The archive plaintext from W12.3—containing the retired certificate, rollover record (IDREL-COL-R4), and the wrapped PKCS8—plus the unwrapped historical Ed25519 private key from W12.3.

**Campaign references:** No separately named capability output.

## Completion and downstream use

Recover fresh data through the still-restricted collection service with the correct current identity and revision. Replaying the historical archive is insufficient. This completes the W12 operation.

## Difficulty and inspiration

An authored cross-revision identity and collection-protocol composition beyond archive recovery.

**Inspiration:** [Confinement (HTB Cyber Apocalypse 2024; Hard)](../../reference-catalog.md#c17). Confinement supplies collector and archive reconstruction. The historical-to-current collection continuation is an authored extension.

## Technical design

### Surface and normal behavior

**Prerequisite gate:** The participant must have completed W12.3 (`cold_archive_recovered` state flag set by the archive service).

The `archive.collection-path` route in the archive client document → POST `retained-archive.arwc.test/api/collection-paths/current`. The route handles two operations:

**Operation `exchange`:** The participant presents the historical identity—the retired certificate (PEM, from archive plaintext), the rollover record (from archive plaintext), a fresh nonce, and an Ed25519 signature proof over `collect-archive/v3|CUR-COL-CRR-R11|R11|<nonce>`. The service:
1. Verifies the certificate against the archive enrollment CA (RSA, `Alterra Archive Enrollment CA`)
2. Verifies the rollover record matches the server-side expected rollover and that the CA signed it
3. Verifies the proof signature against the certificate's Ed25519 public key
4. Checks the certificate subject OU is `svc-field-collection`
5. Issues a 10-minute read-only session token for `CUR-COL-CRR-R11`

The session is single-use: a second exchange attempt while a valid session exists returns 409. The replay protection uses the nonce in the signed message.

**Operation `read`:** Presents the session token and requests dataset `CUR-COL-CRR-R11` at revision 11. Returns the current collection record for asset AST-CRR-017 / outlet group OG-CRR-02.

**The vulnerability:** The collect-archive/v3 token exchange verifies the certificate chain and rollover signature but does not check the `retired_subject` flag in the rollover record (which is `true`). A retired identity can therefore obtain a live session for the current dataset.

Native bindings:

- Route: `archive.collection-path` → POST `retained-archive.arwc.test/api/collection-paths/current`
- Inputs from W12.3 archive plaintext: `retired_client_certificate` (PEM), `rollover` dict
- Historical private key: Ed25519 PKCS8 unwrapped in W12.3
- Dataset returned: CUR-COL-CRR-R11, asset=AST-CRR-017, outlet_group=OG-CRR-02

### Vulnerability and intended solution

The authored condition is **historical-to-current identity rollover**. The `exchange` operation verifies the certificate chain and rollover signature but omits the retired-subject check before mapping `svc-field-collection` through IDREL-COL-R4. The participant:

1. Extracts the retired certificate PEM and rollover dict from the W12.3 archive plaintext.
2. Uses the unwrapped Ed25519 private key (from W12.3) to sign the proof message.
3. Submits `operation: "exchange"` with the certificate, rollover, nonce, and signed proof.
4. Uses the returned session token with `operation: "read"` and dataset `CUR-COL-CRR-R11` at revision 11.

The result proves that the archived identity retains a path to live data through the rollover, giving old collection intelligence operational value.

### Evidence and completion

The archive service writes an immutable audit for both `collection-session/exchange` and `collection-session/read`. The read result (`CUR-COL-CRR-R11`) is the current protected dataset, not archival content. Evidence sources are `features.a-corporate.a-archive`.

### Boundaries and persistence

`current_data_observed` state flag persists across restarts. The collection session expires after 10 minutes; retrying read with the same token succeeds within that window. A second exchange attempt while a session is active returns 409.

### Author checks

Verify that the exchange succeeds with the correct certificate, rollover, nonce, and signed proof. Test wrong OU, wrong rollover, bad proof, and replay. Confirm denial without W12.3 prerequisite. Verify the read returns the correct dataset and that an expired or reused session is denied.

## Hints

### Hint 1

The archive plaintext from W12.3 contains the `retired_client_certificate` (PEM) and `rollover` dict, including IDREL-COL-R4 and its CA-signed signature. These are the exchange inputs. The historical private key (PKCS8 from W12.3) is an Ed25519 key—use it to sign the proof.

### Hint 2

Construct the proof by signing the message `collect-archive/v3|CUR-COL-CRR-R11|R11|<nonce>` with the historical Ed25519 key. Submit it with `operation: "exchange"` to the `archive.collection-path` route. The service does not check the `retired_subject: true` flag in the rollover record, so the retired identity succeeds.

### Hint 3

After a successful exchange, use the returned `collection_session` token with `operation: "read"` to retrieve dataset CUR-COL-CRR-R11 at revision 11. This is the current protected data for the archived maintenance identity. The session expires in 10 minutes and a second exchange while it is active returns 409.
