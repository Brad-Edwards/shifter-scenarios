## Challenge description — player-facing

Recover the historical collector associated with the archive lead and restore it as a usable analysis artifact.

## Story purpose

Continues the intelligence trail from contractor or lineage evidence.

## Prerequisites and starting position

**Required access or evidence:** [W08.4](../W08/W08.4.md) OR [W11.3](../W11/W11.3.md).

**Starting material:** The archive service client document, the quarantine object QTN-COL-2019-12 in AQTN1 format, and the collector binary in a Gitea repository.

**Campaign references:** No separately named capability output.

## Completion and downstream use

Recover the actual collector and its archive binding. The verified collector SHA256 is submitted to the archive service, which writes the completion audit. There is no objective to deploy it or damage data.

## Difficulty and inspiration

A bounded recovery task requiring binary format parsing (offline crypto analysis) and Gitea repository access.

**Inspiration:** [Confinement (HTB Cyber Apocalypse 2024; Hard)](../../reference-catalog.md#c17). Confinement supplies collector and archive reconstruction. The historical-to-current collection continuation is an authored extension.

## Technical design

### Surface and normal behavior

**Prerequisite gate:** The participant must first submit the LIN-AST-CRR-017-R8 lineage record (from W11.3) to `planning.lineage-record` (POST `planning-data.arwc.test/api/lineage-records/current`). This writes the archive-lineage evidence to the shared planning-evidence volume, which the archive service reads. Without this submission, the archive service returns HTTP 403 for the quarantine route.

The `archive.quarantine-collector` route in the archive client document → GET `retained-archive.arwc.test/api/collectors/quarantine`. Returns the quarantine object record QTN-COL-2019-12 with AQTN1 format metadata, a download link for the AQTN1 artifact, the collector repository path (`arwc-archive/retained-collectors`), and the Gitea reader access token.

**AQTN1 binary format** (the offline crypto analysis): The participant downloads `QTN-COL-2019-12.aqtn` via `GET /api/artifacts/QTN-COL-2019-12.aqtn`. The file has the following frame structure:

```
magic (5 bytes): b"AQTN1"
metadata_length (4 bytes, big-endian)
payload_length (8 bytes, big-endian)
sha256_digest (32 bytes) — SHA-256 of the encrypted payload
build_id_length (2 bytes, big-endian)
build_id (N bytes): b"COLLECT-CRR-12"
nonce (12 bytes)
metadata_header (JSON, metadata_length bytes)
encrypted_payload (payload_length bytes)
```

Parsing the metadata_header JSON reveals `collector_build_id: "COLLECT-CRR-12"` and `archive_id: "ARC-COLD-CRR-2019"`. The encrypted payload is the cold archive (decryption is W12.2–W12.4, not required here).

**Gitea access:** The quarantine response includes `collector_repository: "arwc-archive/retained-collectors"` and `collector_access_token`. The participant fetches the collector binary via the Gitea API: `GET https://engineering.arwc.test/api/v1/repos/arwc-archive/retained-collectors/contents/collector-crr` with `Authorization: token <collector_access_token>`. The response includes the base64-encoded binary.

**Completion:** After downloading the collector binary, the participant verifies its SHA256 and submits via `archive.collector-recovery` (POST `retained-archive.arwc.test/api/collector-recoveries`) with `{"collector_sha256": "<sha256>"}`. The archive service validates the SHA256 against the collector manifest and writes the completion audit.

Native bindings:

- Prerequisite: `planning.lineage-record` route → POST to `planning-data.arwc.test/api/lineage-records/current`
- Quarantine: `archive.quarantine-collector` route → GET `retained-archive.arwc.test/api/collectors/quarantine`
- AQTN1 artifact: `GET /api/artifacts/QTN-COL-2019-12.aqtn`
- Collector binary: Gitea API `GET https://engineering.arwc.test/api/v1/repos/arwc-archive/retained-collectors/contents/collector-crr`
- Completion: `archive.collector-recovery` route → POST `retained-archive.arwc.test/api/collector-recoveries`

### Vulnerability and intended solution

This card is a discovery and binary-format analysis task. The AQTN1 binary frame encodes the collector build identity and archive binding in a parseable header. The encrypted payload is not decryptable at this stage. The participant:

1. Submits the W11.3 lineage record to unlock quarantine access.
2. Reads the quarantine object to find the AQTN1 artifact download and Gitea reference.
3. Downloads and parses the AQTN1 binary format to identify the collector build ID and archive.
4. Uses the Gitea API with the provided access token to download the collector binary.
5. Verifies the SHA256 and submits proof to the archive service.

The required result is: Recover the actual collector and its archive binding. The archive service writes the completion audit after the verified SHA256 submission.

### Evidence and completion

The archive service writes an immutable audit for the accepted collector-recovery request. The audit action is `collector-recovered`. Evidence sources are `features.a-corporate.a-archive`. A wrong SHA256, unreached quarantine object, or missing lineage prerequisite returns an error without writing audit state.

### Boundaries and persistence

The result remains local evidence unless a downstream workflow explicitly names it. `quarantine_observed` and `collector_recovered` state flags persist across restarts. The collector-crr binary persists in the Gitea repository across resets.

The behavior is limited to the named fictional objects and bounded service operation. It provides no general shell, arbitrary network target, unrelated district access, real process interface, or authority not expressly declared by the card.

### Author checks

Build and test the normal baseline first. Exercise the exact authored path and verify the named result plus its immutable audit. Test wrong SHA256, missing lineage prerequisite, unreached quarantine, and each denial boundary. Confirm that AQTN1 parsing correctly identifies COLLECT-CRR-12 and ARC-COLD-CRR-2019. Verify the Gitea download returns the correct binary and that SHA256 verification passes.

## Hints

### Hint 1

The lineage record from W11.3 is the prerequisite. Submit it to the `planning.lineage-record` route in the planning service client document. The archive service will then allow access to the quarantine collector route.

### Hint 2

The quarantine object is in AQTN1 binary format. After downloading the artifact, parse the binary frame: the first 5 bytes are the AQTN1 magic, followed by fixed-width length and digest fields. The build ID and a JSON metadata header follow and identify the collector without requiring decryption of the payload.

### Hint 3

The quarantine response includes both the Gitea repository path and an access token. Use the Gitea API endpoint `/api/v1/repos/<org>/<repo>/contents/<file>` with the provided token to download the binary. Decode the base64 `content` field to get the collector-crr binary, verify its SHA256, and submit it to the `archive.collector-recovery` route.
