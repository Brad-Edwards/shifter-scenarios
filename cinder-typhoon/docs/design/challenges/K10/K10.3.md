## Challenge description—player-facing

Deliver a crafted support document that crosses the viewer's intended isolation boundary and recovers the protected preview content.

## Story purpose

Completes an application-exploitation branch with actual restricted information.

## Prerequisites and starting position

**Required access or evidence:** [K10.2](K10.2.md).

**Starting material:** The K10.2 collision (document_id `DOC-9BC054D6F95DFA6A` shared by both source URLs), the `preview.render` route on `preview.keplerops.test`, and the participant's source URL `http://sup.keplerops.test/attachment/sup-k-2841`.

**Campaign references:** No separately named capability output.

## Completion and downstream use

Recover the protected content through a fresh preview interaction. A binding collision without access to the other document is insufficient.

## Difficulty and inspiration

A substantive isolation and delivery problem directly inspired by Postviewer v3.

**Inspiration:** [Postviewer v3 (Google CTF 2024; 19 solves, no formal tier)](../../reference-catalog.md#c09). Uses Postviewer v3's isolated-document binding problem; its original solve count is not a tier label.

## Technical design


### Surface and normal behavior
The preview service accepts a participant-submitted HTML document via `POST /api/preview/render` and sends it to Gotenberg (Chromium) for rendering. The rendered PDF is returned. Gotenberg runs at port 3000 internally. The service also runs an internal document server at 127.0.0.1:9000 that serves protected preview content—this endpoint binds only to loopback and the participant cannot reach it directly from outside the container.

### Vulnerability and intended solution

The `preview.render` route accepts participant-crafted HTML. The service forwards the HTML to Gotenberg unchanged. Chromium renders the HTML inside the container and can reach internal services via `127.0.0.1`. `CHROMIUM_DENY_PUBLIC_IPS=true` blocks external IP access but does not block loopback.

The internal server at `http://127.0.0.1:9000/protected-preview/{document_id}` serves the protected document for a given document_id. When the participant's HTML causes Chromium to fetch that URL, the internal server records the access and serves maya.ranscombe's protected HTML back to Chromium. Chromium renders the fetched content into the PDF.

The intended solution:
1. Know the target document_id `DOC-9BC054D6F95DFA6A` from K10.1 and K10.2.
2. Craft HTML that makes Chromium fetch `http://127.0.0.1:9000/protected-preview/DOC-9BC054D6F95DFA6A` (via iframe or JS fetch).
3. POST the crafted HTML to `POST /api/preview/render` with `{"html": "...", "source_id": "sup-k-2841", "document_id": "DOC-9BC054D6F95DFA6A"}`.
4. Gotenberg/Chromium renders the HTML, fetches the internal resource, and embeds the protected content in the PDF.
5. The internal server records the boundary crossing.
6. The service returns `ssrf_confirmed: true`, the protected case metadata, and the render_digest.
7. Two audit records are written: `preview-ssrf-access` and `protected-content-reads`.

The participant cannot reach `127.0.0.1:9000` directly—only Chromium can. Gotenberg's sandbox and network settings are not weakened.

### Evidence and completion
The service emits a `preview-ssrf-access` audit record (Chromium-to-internal-server boundary crossing) and a `protected-content-reads` record (protected version + render digest). The JSON response contains `ssrf_confirmed: true`, `protected_case_id=CAS-MAYA-2841`, `owner=maya.ranscombe`. Both audit records are required for objective evaluation.

### Boundaries and persistence

Preview-only disclosure. Participant-created service state persists for the life of the participant world and ordinary retries do not erase it. The action is limited to the exact records, identities, routes, and destination effects declared here; unrelated tenants and services remain denied. Infrastructure recovery and submission adjudication are outside this in-world contract.

### Author checks
Test normal own preview without SSRF (ssrf_confirmed: false), SSRF with correct document_id (ssrf_confirmed: true + audit records), unknown document_id (404 from internal server), and that 127.0.0.1:9000 is not reachable from outside the container.

## Hints

### Hint 1

The `preview.render` route is at `POST /api/preview/render` (see `preview.keplerops.test/.well-known/fieldkest-client`). It accepts `{"html": "<crafted-html>", "source_id": "sup-k-2841", "document_id": "DOC-9BC054D6F95DFA6A"}`. The service sends the HTML to Gotenberg unchanged—Chromium renders what the participant submits.

### Hint 2

The preview service runs an internal document server at `127.0.0.1:9000`. This server exposes `GET /protected-preview/{document_id}` and returns the protected HTML for that slot. The endpoint binds to loopback only—the participant cannot reach it directly. Only Chromium (running inside the container) can reach `127.0.0.1`. Craft an HTML document with an `<iframe src="http://127.0.0.1:9000/protected-preview/`DOC-9BC054D6F95DFA6A`">` or a JS fetch to that URL.

### Hint 3

Submit the crafted HTML to `POST /api/preview/render`. When Chromium fetches the internal resource, the service records the access and returns `ssrf_confirmed: true`, `protected_case_id=CAS-MAYA-2841`, `owner=maya.ranscombe`, and `render_digest`. The `preview-ssrf-access` and `protected-content-reads` audit entries confirm the boundary crossing and cannot be forged.
