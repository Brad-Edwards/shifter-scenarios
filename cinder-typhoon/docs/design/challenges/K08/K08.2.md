## Technical design


### Surface and normal behavior
The compatibility record refers to a key identifier, derivation version, and archived encryption-context metadata stored in the FieldKest release archive.

### Vulnerability and intended solution

The v2 entitlement record `ENT-ARWC-DIAG-0698-V2.json` in the same Gitea CRR-OG2 directory carries an `expiry_policy` field as a top-level metadata entry—this is the missing encryption context. The v2 checker (`checker=v2`) derives the AES-256-GCM key using `HKDF(info = base_info + "|" + expiry_policy)` where `expiry_policy` is read from the participant-supplied record.

The intended solution:
1. Navigate to the v2 record in Gitea (`ENT-ARWC-DIAG-0698-V2.json`).
2. Observe that the record has schema `fieldkest.entitlement-record/v2` and an `expiry_policy` top-level field.
3. POST to `packages.entitlement-check` with `checker=v2` and the v2 record (including the `expiry_policy` field).
4. The v2 checker reads `expiry_policy` from the record body, derives the v2 HKDF key, and decrypts. The result is `state=legacy-test-accepted` with `revision=3` (distinct from the v1 baseline).

The "missing encryption context" is the `expiry_policy` field: the v1 checker does not include it in key derivation, but v2 does. Without the correct `expiry_policy` in the posted record, the v2 key derivation uses an empty string and decryption fails (422).

### Evidence and completion
The checker accepts the recovered context only when it decrypts/verifies the supplied record and binds it to the expected legacy revision.

### Boundaries and persistence

Cryptographic context for K08.3 Participant-created service state persists for the life of the participant world and ordinary retries do not erase it. The action is limited to the exact records, identities, routes, and destination effects declared here; unrelated tenants and services remain denied. Infrastructure recovery and submission adjudication are outside this in-world contract.

### Author checks
Verify incomplete context fails, expected context validates one record, wrong revision/key ID fails, no other archive object opens.

## Hints

### Hint 1

The v2 entitlement record is in the same Gitea CRR-OG2 directory as the v1 record, named `ENT-ARWC-DIAG-0698-V2.json`. It has `schema=fieldkest.entitlement-record/v2` and an `expiry_policy` top-level field. This field is the missing context that the v2 checker uses for key derivation.

### Hint 2

The v2 checker reads `expiry_policy` from the participant-supplied record body and appends it to the base HKDF info: `info = "fieldkest/ENT-ARWC-DIAG-0698/FLK-6.9.8" + "|" + expiry_policy`. Supplying the v2 record with its `expiry_policy` to `packages.entitlement-check` with `checker=v2` constructs the correct key. Without `expiry_policy`, the checker uses an empty string and decryption fails (422).

### Hint 3

The result is `state=legacy-test-accepted` with `revision=3` (the v2 record seals a revision-3 plaintext, distinct from the v1 baseline at revision 4). This is the evidence for K08.2 completion and the starting context for K08.3.
