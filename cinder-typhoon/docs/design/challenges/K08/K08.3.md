## Challenge description — player-facing

Create an alternative entitlement the legacy checker accepts while preserving the required customer and feature binding.

## Story purpose

Completes the legacy-license branch with an unauthorized accepted entitlement.

## Prerequisites and starting position

**Required access or evidence:** [K08.2](K08.2.md).

**Starting material:** The K08.2 v2 HKDF key derivation parameters (ikm, salt, base_info, expiry_policy, aad), the plaintext template `ENT-ARWC-DIAG-0698-plaintext-template.json` in the Gitea CRR-OG2 directory, and the `packages.entitlement-check` endpoint with checker=v2.

**Campaign references:** No separately named capability output.

## Completion and downstream use

Obtain acceptance for a distinct, correctly scoped entitlement. It does not confer customer execution or modern release-signing authority.

## Difficulty and inspiration

Requires constructing an accepted alternative under the retained legacy cryptographic constraints.

**Inspiration:** [Tsayaki (HTB Cyber Apocalypse 2024; Hard)](../../reference-catalog.md#c06). Retains Tsayaki's legacy cryptographic entitlement problem; this concerns an obsolete component.

## Technical design


### Surface and normal behavior
The legacy entitlement checker validates a customer, feature, expiry, and compatibility integrity field before enabling a test entitlement in the isolated service.

### Vulnerability and intended solution

The v2 HKDF key (derived using `base_info + "|" + expiry_policy`) is recoverable from K08.2's successful checker result. The legacy checker validates: schema, record_id, customer_id, feature_id, and package_revision — but does not enforce a specific revision or plaintext hash. The current policy (v1 checker, baseline sha256) would reject the alternate, but the legacy (v2) checker accepts any correctly encrypted and bound plaintext.

The intended solution:
1. Read the plaintext template from Gitea (`ENT-ARWC-DIAG-0698-plaintext-template.json`).
2. Fill in the actual `expiry_policy` (from K08.2 result) and choose a `revision` ≠ 4 (and ≠ 3 to differ from K08.2).
3. Serialize the plaintext as canonical JSON (sorted keys, no spaces).
4. Encrypt with the v2 HKDF key and a fresh nonce using AES-256-GCM with aad=`"ENT-ARWC-DIAG-0698|TEN-ARWC-019|FLK-6.9.8"`.
5. Construct the full record JSON (cipher, ciphertext, nonce, tag, metadata) and POST with checker=v2 and the K08.2 context.
6. The checker accepts and returns `state=legacy-test-accepted` with the participant's chosen revision.

The checker enforces the customer/feature binding: wrong customer_id or feature_id returns 422. The current-policy checker (v1) also returns 422 (wrong key derivation). Only v2 with the correct expiry_policy accepts the alternate.

### Evidence and completion
The service records legacy acceptance, customer/feature binding, and test entitlement state; a text artifact alone does not satisfy the result.

### Boundaries and persistence

No package/customer authority Participant-created service state persists for the life of the participant world and ordinary retries do not erase it. The action is limited to the exact records, identities, routes, and destination effects declared here; unrelated tenants and services remain denied. Infrastructure recovery and submission adjudication are outside this in-world contract.

### Author checks
Test current checker rejection, intended legacy acceptance, wrong customer/feature rejection, expiry handling, no cross-service effect.

## Hints

### Hint 1

Navigate to the Gitea CRR-OG2 directory and read `ENT-ARWC-DIAG-0698-plaintext-template.json`. It shows the required plaintext fields: schema, record_id, customer_id, feature_id, package_revision, expiry_policy (from K08.2), and revision (choose any integer ≠ 4 and ≠ 3). Serialize with sorted keys and no spaces (canonical JSON) before encrypting.

### Hint 2

Encrypt the canonical JSON plaintext with AES-256-GCM: use the v2 HKDF key (`HKDF(info=base_info+"|"+expiry_policy)` from K08.2), a fresh 12-byte random nonce, and aad=`"ENT-ARWC-DIAG-0698|TEN-ARWC-019|FLK-6.9.8"`. Build the entitlement record JSON with cipher, ciphertext_base64, nonce_hex, tag_base64, and the top-level metadata fields (including expiry_policy).

### Hint 3

POST to `packages.entitlement-check` with checker=v2, the crafted record (including expiry_policy), and the K08.2 HKDF context. Wrong customer_id or feature_id returns 422; checker=v1 also returns 422. A correct alternate entitlement returns state=legacy-test-accepted with the participant's chosen revision.
