## Challenge description — player-facing

Deliver a compatible training formatter that adds Cinder's rehearsal marker to the intended consumer's delivery report.

## Story purpose

Completes a miniature supplier-to-consumer episode.

## Prerequisites and starting position

**Required access or evidence:** [T03.2](T03.2.md).

**Starting material:** The training repository, retained build diagnostics, a sample package, and the rehearsal publication/consumer interfaces.

**Campaign references:** No separately named capability output.

## Completion and downstream use

Demonstrate a fresh consumer report with the marker and preserved ordinary behavior. Publication without consumption is insufficient.

## Difficulty and inspiration

A bounded interface adaptation and consumer-binding problem.

**Inspiration:** Original challenge for this campaign.

## Technical design

### Surface and normal behavior

`PUT /api/packages/@cinder/delivery-formatter/{version}` on
`developer.training:8083` accepts bearer-authenticated JSON containing exactly
`name`, matching `version`, and `files` with UTF-8 `package.json` and `index.js`.
The body limit is 256 KiB. Only a new stable version greater than 1.4.0 and
below 2.0.0 is accepted; versions are immutable and canonically SHA-256 hashed.
`POST developer.training:8084/api/consumer/run` resolves the highest compatible
stable version afresh, invokes its `formatDelivery` export once with the fixed
DL-204 input, and records version, package digest, input, output, output digest,
receipt ID, and acceptance time. `/consumer-contract.md` independently defines
DF-1 and the permitted `rehearsal_marker`; T03.1 is not required.

### Vulnerability and intended solution

The intended solution publishes a compatible version using T03.2's pre-existing
scope, preserves all DF-1 fields and summary, and adds only
`"rehearsal_marker":"Cinder rehearsal"`, then invokes a fresh consumer run.
The worker has a two-second limit, 64 MiB memory, no network, an empty
environment, a read-only filesystem, and one invocation. Invalid output returns
422 and creates no successful report; publication without a consumer receipt is
insufficient.

### Evidence and completion

The registry retains publication time and revision. The independent consumer
records the subsequently resolved version and digest and produces a fresh
report containing the rehearsal marker while preserving ordinary fields.
An unused published version has no corresponding consumer receipt.

### Boundaries

The registry scope, consumer tenant, and report data belong to the individual
workspace. Packages cannot affect other consumers, external package resolution,
or later campaign systems. Published versions and consumer receipts persist
across attempts and breaks.

### Author checks

Check baseline consumer output, incompatible-version rejection, compatible
resolution, preserved report fields, receipt correlation, private consumer
scope, and persistence of versions and receipts across attempts.
