## Challenge description — player-facing

Use the identity evidence you recovered to take control of the rehearsal account through its recovery workflow and retrieve its private handover.

## Story purpose

Makes the identity trail produce actual account access.

## Prerequisites and starting position

**Required access or evidence:** ([T02.1](T02.1.md) AND [T02.2](T02.2.md)).

**Starting material:** The rehearsal identity desk, candidate account notes, a public directory, recovery workflow, and assignment service.

**Campaign references:** No separately named capability output.

## Completion and downstream use

Demonstrate the recovered identity and obtain its private handover. A recovery acknowledgement without usable access is insufficient. The session enables T02.4.

## Difficulty and inspiration

One explicit recovery workflow after two short evidence tasks.

**Inspiration:** Original challenge for this campaign.

## Technical design

### Surface and normal behavior

`POST /api/recovery/redeem` accepts exactly the JSON fields `account`,
`case_fragment`, and `staff_detail`. Only the tuple `rhea.moss`, `CASE-7Q4M`,
and `Blue cabinet 17` succeeds. It returns 201 and creates a 32-random-byte,
unpadded-base64url session for `rhea.moss`, also usable as the HttpOnly,
SameSite=Strict `CINDER_REHEARSAL_SESSION` cookie. The redemption is single-use;
the server-side session persists for the environment lifetime. `GET
/api/handover` requires that session and returns only Rhea's private handover.

### Vulnerability and intended solution

The workflow treats the two independently disclosed values plus the public
account name as ownership proof. A missing or wrong value returns 403; malformed
or extra fields return 400; a second redemption returns 409 without invalidating
the original session. The intended solution supplies the exact outputs of
T02.1 and T02.2, then proves access by reading the authenticated handover.

### Evidence and completion

Recovery creates a session tied to the rehearsal subject. The authenticated
handover read returns that subject's private document and has its own service
audit. The same session remains usable at the assignment service, including
after a break or day-two resume.

### Boundaries

The session authenticates only this training subject. It can read the subject's
handover and use the assignment service, including the deliberately flawed
assignment authorization in T02.4. It cannot change recovery factors, password,
directory records, or any non-training application. There is no short expiry
that makes a break or day-two resume lose acquired access. Neither handover
reads nor assignment attempts revoke the session.

### Author checks

Check that each insufficient factor set fails; verify one recovery redemption,
repeated own-handover reads, denial of another subject's handover, and the same
identity at the assignment service. Verify continuity after a break and
day-two resume.
