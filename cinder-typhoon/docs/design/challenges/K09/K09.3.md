## Challenge description—player-facing

Make the test job consume a support input outside the collection its ordinary form allows. Recover the restricted review output it produces.

## Story purpose

Crosses a build-input boundary before attempting execution.

## Prerequisites and starting position

**Required access or evidence:** [K09.2](K09.2.md).

**Starting material:** The K09.2 `integration-review-input-v3.json` artifact (with `diagnostic_eligible: true` and `linked_support_ref: "buildops://reviews/diagnostic-request-reference@3"`), and the `ci.review-jobs` route on `review.keplerops.test`.

**Campaign references:** No separately named capability output.

## Completion and downstream use

Produce the protected review output under the intended job identity. This establishes a distinct input capability, not general runner execution.

## Difficulty and inspiration

One application input boundary with a small job/artifact join.

**Inspiration:** Original challenge for this campaign.

## Technical design


### Surface and normal behavior
The CI test job consumes an archived support input and generates a restricted
review output under the runner's job identity. The protected review includes
the maintained diagnostic request reference: profile names, command argument
format, and the internal runner note's path. It contains neither the private note
nor worker credentials. The reference is an ordinary Build Operations document,
not an instruction to exploit the job. A completed review returns a retained
input reference bound to the resolved object/revision, submitting account, and
workspace generation. Later diagnostic jobs use that reference; receiving it is
ordinary review behavior, not an objective evaluation-triggered grant. The input's integration
classification is service-owned metadata, not a caller-editable field.

### Vulnerability and intended solution

The review job endpoint (`POST /api/review-jobs` on `review.keplerops.test`) validates the `support_input.artifact_id` and `diagnostic_eligible` flag. When submitted with the K09.2 integration artifact (`ART-BLD-1842-INTEGRATION-REVIEW`, `diagnostic_eligible: true`), it follows the `linked_support_ref = "buildops://reviews/diagnostic-request-reference@3"` to resolve the integration reference, returning the content of the diagnostic-request-reference document as `review.maintained_reference`.

The intended solution:
1. Submit `POST /api/review-jobs` with `{"support_input": <K09.2 artifact>, "diagnostic": {"profile": "render-review"}}`.
2. `GET /api/review-jobs/{run_id}` returns state=success, profile=render-review, workspace_generation=WS-ROWAN-2026-09-G1.
3. `review.maintained_reference` = the diagnostic-request-reference content (contains "POST /api/review-jobs" and "/srv/fieldlink-ci/runner/runner-operations.md" but NOT "FieldKest runner service connections").
4. `support_input` = `"buildops://reviews/diagnostic-request-reference@3"` (the integration reference used in K09.4).

Ordinary inputs (`diagnostic_eligible: false`) yield a different `support_input` and cannot access the integration diagnostic context.

### Evidence and completion
CI records the selected support object and returns the restricted review output with job provenance; no persistent runner access is granted.

### Boundaries and persistence

Required command-dispatch input Participant-created service state persists for the life of the participant world and ordinary retries do not erase it. The action is limited to the exact records, identities, routes, and destination effects declared here; unrelated tenants and services remain denied. Infrastructure recovery and submission adjudication are outside this in-world contract.

### Author checks
Test normal input, intended linked-object read, arbitrary reference denial, correct job provenance, no execution authority yet.

### Hint 1

Take the K09.2 `integration-review-input-v3.json` artifact and submit it to `POST /api/review-jobs` on `review.keplerops.test` (the `ci.review-jobs` route). ### Hint 2

`GET /api/review-jobs/{run_id}` returns the result. It includes `state=success`, `workspace_generation=WS-ROWAN-2026-09-G1`, `review.maintained_reference` (the diagnostic-request-reference content), and `support_input` (the integration reference for K09.4).

### Hint 3

The `review.maintained_reference` contains "POST /api/review-jobs" and "/srv/fieldlink-ci/runner/runner-operations.md" (from the diagnostic-request-reference document) but NOT "FieldKest runner service connections" (that's in the runner-operations note itself). The returned `support_input = "buildops://reviews/diagnostic-request-reference@3"` is the K09.4 input.
