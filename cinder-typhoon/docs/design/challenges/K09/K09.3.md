## Challenge description — player-facing

Make the test job consume a support input outside the collection its ordinary form allows. Recover the restricted review output it produces.

## Story purpose

Crosses a build-input boundary before attempting execution.

## Prerequisites and starting position

**Required access or evidence:** [K09.2](K09.2.md).

**Starting material:** The developer's build history, ordinary job interface, artifact references, and a sample FieldKest build.

**Campaign references:** No separately named capability output.

## Completion and downstream use

Produce the protected review output under the intended job identity. This establishes a distinct input capability, not general runner execution.

## Difficulty and inspiration

One application input boundary with a small job/artifact join.

**Inspiration:** Original challenge for this campaign.

## Technical design


### Surface and normal behavior
The CI test job consumes an archived support input and generates a restricted
review output under the runner's job identity. The protected review includes
the maintained diagnostic request reference: profile names, command argument
format, and the internal runner note's path. It contains neither the private note
nor worker credentials. The reference is an ordinary Build Operations document,
not an instruction to exploit the job. A completed review returns a retained
input reference bound to the resolved object/revision, submitting account, and
workspace generation. Later diagnostic jobs use that reference; receiving it is
ordinary review behavior, not an objective evaluation-triggered grant. The input's integration
classification is service-owned metadata, not a caller-editable field.

### Vulnerability and intended solution
The job input resolver validates the submitted collection but follows a linked support reference outside it. The intended solution creates a bounded valid input using K09.2's artifact and observes the review result.

### Evidence and completion
CI records the selected support object and returns the restricted review output with job provenance; no persistent runner access is granted.

### Boundaries and persistence

Required command-dispatch input Participant-created service state persists for the life of the participant world and ordinary retries do not erase it. The action is limited to the exact records, identities, routes, and destination effects declared here; unrelated tenants and services remain denied. Infrastructure recovery and submission adjudication are outside this in-world contract.
