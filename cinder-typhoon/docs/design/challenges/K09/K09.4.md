## Challenge description — player-facing

Use the review job to retrieve Build Operations' private runner note and verify the build-record connection it describes.

## Story purpose

Turns build access into a useful scoped execution foothold.

## Prerequisites and starting position

**Required access or evidence:** [K09.3](K09.3.md).

**Starting material:** The developer's build history, ordinary job interface, artifact references, and a sample FieldKest build.

**Campaign references:** No separately named capability output.

## Completion and downstream use

Demonstrate execution as the build worker, retrieve its protected note, and make a second authenticated request to the build-record status service through the same job submission path. The repeatable job path supplies the existing workload, identity, and maintenance starting access, not their later results. It grants no customer execution.

## Difficulty and inspiration

Remains Medium: adapt the previously recovered support-input structure to cross
one additional authorization boundary, then verify the resulting access with a
documented command. There is no new credential hunt, shell exploit, timing
condition, or compulsory downstream solve. Running the documented check demonstrates
the same capability rather than introducing a second exploit. Fresh assisted
solves must still confirm this proposed rating.

**Inspiration:** Original challenge for this campaign.

## Technical design

### Surface and normal behavior

The review job accepts a support-input reference and a diagnostic request. Its
ordinary `render-review` profile produces a review document. Build Operations
also uses `runner-command` to investigate failed integrations. It launches a
non-privileged process with an argument vector inside an isolated job environment,
initially authenticated to services as `svc-fieldlink-ci`. A command may invoke
a POSIX shell, run a script, use ordinary HTTP/certificate/directory clients,
read its own files, and save output. This is actual command execution, not a
fixed list of service requests or simulated command responses.

The job has a private persistent `/workspace`, authenticated file upload/download
through the submitting account's job interface, and fresh per-run credential
files under `/run/fieldlink-ci`. The operations note and per-run configuration
are mounted read-only. `connections.env` supplies only non-secret base URLs;
each per-service curl configuration supplies that service's worker authentication
and certificate trust, with no forced URL, HTTP method, request body, or automatic
redirect following. The installed `curl` accepts the documented options.
Runtime processes and temporary files disappear
at job exit; the account's workspace and saved results remain. Client tools
required by the selected downstream mechanisms must already be installed;
internet access or installing a missing tool is not an additional task.

K09.3's protected review includes the maintained diagnostic request reference,
with the two profile names, argument format, and the internal note's path. It
does not execute that profile or return the protected note.
The note identifies the worker, lists its existing service connections, and
gives a harmless build-record status command. It also explains how to use an
independently obtained identity without the worker's authentication overriding
it. Job history retains argument vectors, run IDs, exit status, standard output,
standard error, and owned artifacts. The input can be submitted again from the
existing developer position, with credentials retained in private files rather
than embedded in the saved command line.

### Vulnerability and intended solution

The job's normal JSON request contains `support_input` (the retained input
reference) and a `diagnostic` object. `runner-command` takes `argv`, a non-empty
array of strings, and starts that program directly in `/workspace`. Shell syntax
is available by explicitly invoking `/bin/sh -c`; it is not interpreted implicitly.
The request cannot select a runtime image, operating-system identity, mounts,
network policy, another account's workspace, or the CI controller. The protected
reference and note are authored in
[the Build Operations assets](../../../../assets/keplerops/build-operations/README.md)
and placed only on their owning CI node by native SDL content declarations.

The job checks the caller's right to submit a support review but fails to check
the separate Build Operations entitlement when dispatching the diagnostic
profile supplied alongside the resolved support input. Command dispatch requires
the retained input reference from a completed integration review: the service
binds it to the resolved object/revision, submitting account, and reset generation.
That reference is returned by normal review processing in K09.3, not by scoring.
Only the protected integration input has the server-owned diagnostic eligibility
metadata. An ordinary support input, raw unresolved link, invented reference,
or reference copied from another workspace cannot dispatch commands. The flaw
is trusting that valid integration reference without also checking the caller's
Build Operations entitlement. K09.3 crosses the input-record boundary; K09.4
changes the diagnostic profile and supplies a correctly bound
command request. Reading the reference alone or resubmitting an unchanged review
does not execute participant-selected commands.

The intended first command reads the internal runner note at its documented
path. The player then runs its documented `curl` status check in a second job
and receives the remote service's authenticated response. Both jobs use the configured worker
identity. No completion event creates an account, grants a role, changes a
firewall, or opens a connection. Subsequent commands use the same submission
path, without an extra challenge or a session secretly supplied by scoring.

### Evidence and completion

Require two distinct run IDs bound to the same participant's job workspace:
the first records the executed profile, process identity, actual internal-note
read, and note revision; the second records command execution and the build-record
status response. Join that second run to the service's authenticated request
audit using the per-run credential lease, participant workspace, request ID,
principal, target, and trusted job network origin. The request header alone is not trusted: commands can
choose it. The execution/file-read and credential-lease evidence must be collected
outside the participant-writable job and matched to the receiving service's audit.
A copied note, echoed identity, client-supplied success field, or a job that
never contacted the service cannot satisfy completion.

The status response contains the current worker identity and build-service
availability, not the trust document, backup principal, or maintenance policy.
Those remain separately protected records for K14, K30, and K31. Returning the
note and response is ordinary job behavior, independent of scoring; neither
output announces an unlock or directs the player to a numbered challenge.

### Boundaries and reset

The authorized unit is a repeatable isolated job, not an administrator shell on
the build server. Commands and child processes run without host privilege; no
host paths, device access, runtime socket, CI controller credentials, other job
workspaces, private consumer/reference state, or evidence collector are exposed.
Uploads/downloads enforce account ownership, normalized path containment, and
symlink-safe access. A command can read or copy its own job-scoped credentials;
log masking is not a security boundary and must not be claimed to prevent this.
Only short-lived, per-run worker credentials with the listed resource scope are
mounted. Issuer signing keys and reusable CI administration secrets never enter
the job. A copied worker credential cannot outlive its lease or widen its role;
its destination also restricts use to the issuing job's network origin. Keep
lease validation and source binding outside the job's writable state.

Network enforcement is outside the job. Allow only the declared supplier
service destinations and the actual protocols needed by their selected clients,
with scoped internal DNS and time services where required. No internet, other
participants, host/control infrastructure, cloud metadata, ARWC, general subnet
transit, or reverse listener is available. Direct IPs, redirects, tunnels, and
child processes cannot bypass these restrictions. No automatic credential
injection proxy may overwrite a client's independently selected authentication.

The existing scope is source/package reads; the limited staff and certificate
interfaces; cloud trust and authenticated build records; and maintenance policy
and own-job management. Each destination checks its normal resource and action
permissions. Maintenance management can submit the bounded maintenance workload
used by K31, but cannot select arbitrary images, change its runtime identity,
or directly read the field archive. Recovering the distinct backup or delegated
principal, exploiting maintenance classification, and acquiring staff authority
remain downstream work. An allowed connection is not the destination service's
identity. Source/package access stays read-only under the initial worker role;
commands alone do not grant release approval, signing, or customer delivery.

For a later earned identity, retain its certificate/private key, ticket cache,
or token in the same account's private `/workspace/credentials` and invoke the
real client with that material explicitly. Worker authentication is opt-in
through separate per-service configuration, never an unconditional header or
forced identity. The receiving service must observe the selected principal and
apply that principal's scope. No colleague identity is initially seeded here.
K19 must specify its actual enrollment/authentication protocol and required client
tools; K20 must specify the further delegation interfaces. The runner can use
the existing staff/certificate connections for that work. Where an earned role
is used from the existing developer position instead, its card must identify the
reachable service and credential handoff. Do not invent a new network path or
fake an identity service to fill a missing downstream design.

Finishing a job or this challenge does not revoke the reusable submission path.
Saved inputs, workspace files, and history survive a break and day-two resume;
fresh jobs receive fresh worker credentials through ordinary job setup. Job exit
revokes its worker lease and terminates all child processes, not the separately
earned identities retained in the workspace. Those follow their own issuer's
renewal/recovery policy, documented by the downstream card. A failed command or
job retry leaves earlier files and downstream access intact. Serialize writes
to one account's workspace and allow cancellation of a stuck process without
deleting the workspace. Resource limits must accommodate the required native
clients, return ordinary diagnostics, and introduce no timing puzzle.

An explicit K09 operation reset cancels its jobs, invalidates worker leases,
clears its workspace and mutable job results, and restores initial inputs. It
does not reissue earned identities or erase independent completed evidence;
downstream issuer state follows its own reset scope. Preserved proof from an
older reset generation cannot satisfy a new attempt. A simple job retry is not
an operation reset.

### Author checks

Verify an ordinary review works; K09.1/K09.2 expose no worker credentials;
K09.3 returns the request reference but neither executes participant commands nor
returns the private note. A fresh reader of that reference must be able to
identify the argument format and note path without guessing names or consulting
author notes. Reject guessed profiles with ordinary support inputs, unresolved
links, foreign workspace references, and stale reset generations. Confirm a
normal completed integration review returns its retained reference with scoring
disabled, and retrying it does not consume the reference. Run a harmless command
not present in the documents, a shell
pipeline, and an uploaded script to establish genuine command execution. Verify
stdout, stderr, exit status, files, cancellation, and process cleanup.

Follow the private note's example literally in a second job. Require matching
worker and destination audit records, and deny the same protected read from
the developer identity alone. Reject copied or stale proof, missing destination
audit, wrong principal/target, forged request IDs, participant-written audit
files, and a successful-looking response without a request. With scoring
disabled, both jobs and their returned records must work.

Using only this route, start K14.1, K19.1, K30.1, and K31.1. Verify source/package
reads and staff/certificate requests. Once the downstream designs exist, follow
their real acquisition path, save the earned identity, and use it with its native
client in a fresh job. Require the receiving audit to name that principal rather
than `svc-fieldlink-ci`; an expired or wrong identity must fail rather than fall
back to the worker. A test fixture credential can isolate this client check but
cannot establish a completed downstream solve. Deny host/admin secrets, forbidden
destinations, redirect/tunnel escapes, other job owners, promotion, private
consumer state, direct source database/field archive reads, and ARWC access.
Check that the read-only status example does not complete any downstream task.
Repeat after a break, day-two resume, failed job, and worker credential rotation.
Verify copied worker credentials expire, separate earned material survives job
exit, no background process survives cancellation, and workspace files cannot
change the enforced network or identity policy. Verify operation reset invalidates
old jobs and worker credentials, then a clean solve works again. Observe fresh
assisted solves to confirm Medium difficulty and
that players notice the usable service connections without out-of-world copy.
