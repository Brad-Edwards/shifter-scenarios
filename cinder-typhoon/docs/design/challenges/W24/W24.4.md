## Challenge description — player-facing

The diagnostic service requires a signed authorization to export its private calibration-exception log. Use the recovered signer and its old records to produce an authorization for a fresh export request bound to the current project, then obtain the log.

## Story purpose

Lets Cinder impersonate the diagnostic approver and recover the calibration exceptions omitted from routine support exports. Recovering archived evidence now leads to a distinct breach of the service's approval boundary.

## Prerequisites and starting position

**Required access or evidence:** [W24.3](W24.3.md).

**Starting material:** W24.3's opened bundle supplies the retained signer executable and a finite set of signed diagnostic records with their original metadata. The service supplies its public verification contract, the current project binding, and a fresh read-only export request. The archive-unlock value is already held; the signing key, signing equations, and an authorization for this request are not supplied.

**Campaign references:** No separately named capability output.

## Completion and downstream use

Produce an authorization accepted for the fresh request under the service's existing verification identity and retrieve the corresponding calibration-exception log. Replaying an old approval, substituting a trusted key, or using the archive-unlock value does not satisfy that request. Reconstructing the signer, obtaining signing capability, and its first successful use form one achievement. This authorization is scoped to the diagnostic export and does not supply W15.APPROVAL or CONTROL.

## Difficulty and inspiration

Expert is proposed for combining binary analysis of a custom elliptic-curve signature scheme with mathematical reasoning over the signed records and their metadata. The participant must establish a new signing capability from that evidence. W24.3 has solved only the separate archive-recovery problem; its oracle model and unlock value do not solve the signer.

**Inspiration:** [Curveware (HTB Business CTF 2025; Hard)](../../reference-catalog.md#c32). Retains the executable-to-signature-analysis problem and its metadata weakness. A fresh diagnostic authorization replaces the source's file-recovery payoff. Expert describes the proposed combined analysis, not an automatic promotion of the source rating.

## Technical design


### Surface and normal behavior

`a-diagnostics` and its `diagnostic-services` application own this part of **Signed by someone who never approved it**. Normal behavior applies the declared identity, tenant, object, revision, and process bindings and returns or changes only the caller-scoped object. The exact initial state is: Signer CRR25519-S uses Edwards25519 field p=2^255-19, d=-121665/121666, standard compressed base point, scalar order 2^252+27742317777372353535851937790883648493, little-endian encoding, h=SHA-512(R||A||message) reduced modulo the order, and s=k+h*x mod order; each record leaks nonce bits 60-251 and metadata gives the signed delta between the two records' lower 60-bit nonce portions, permitting recovery of the existing key and one fresh request EXP-CAL-CRR-25.

Native bindings:

- `a-engineering.a-diagnostics/diagnostic-services/signed-by-someone-who-never-approved-it`
- `a-engineering.a-diagnostics/filesystem:/var/lib/arwc-diagnostics/artifacts/signed-by-someone-who-never-approved-it`

The private service-loader contract is `content.arwc-a-diagnostics.w24-4-signed-by-someone-who-never-approved-it`. It freezes accepted and denied requests, state transition, persistence, and evidence; it does not seed a successful result.

### Vulnerability and intended solution

The authored condition is **partial-nonce custom-curve signing-key recovery**. For each retained signature s=k+h*x mod L, metadata gives k>>60 and the signed integer delta between the two low-60-bit nonce portions. Subtracting the two equations cancels the one remaining low nonce unknown: x=((s2-s1)-((k2_hi-k1_hi)<<60)-delta)*inverse(h2-h1,L) mod L. The service rejects the degenerate h2=h1 case, noncanonical points/scalars, replayed messages, and any signature not bound to the fresh canonical EXP-CAL-CRR-25 request bytes and current project revision. The hand build must preserve every named version, encoding, bound, validation order, identity, and unaffected field; substituting a generic vulnerable service would change the task.

The required result is: Produce an authorization accepted for the fresh request under the service's existing verification identity and retrieve the corresponding calibration-exception log. Replaying an old approval, substituting a trusted key, or using the archive-unlock value does not satisfy that request. Reconstructing the signer, obtaining signing capability, and its first successful use form one achievement. This authorization is scoped to the diagnostic export and does not supply W15.APPROVAL or CONTROL.

### Evidence and completion

The owning service writes an immutable audit for the accepted request and result. Caller-supplied output, a local copy, or knowledge of an identifier is not sufficient. Completion is evaluated from fresh service-owned evidence after the action. It cannot issue the identity, create the mutation, move a simulated actuator, or fabricate a downstream acceptance needed to prove itself.

Evidence sources are `features.a-engineering.a-diagnostics`. A wrong identifier, stale revision, replayed one-time value, different checkpoint, or cross-tenant artifact is rejected.

### Boundaries and persistence

The result remains local evidence unless a downstream workflow explicitly names it. Tenant-scoped mutations, sessions that have not expired, generated artifacts, and audits persist across ordinary retries and later sessions. Initial immutable records remain unchanged unless the named route explicitly permits a field-level revision. Infrastructure recovery and submission adjudication are external to the SDL.

The behavior is limited to the named fictional objects and bounded service operation. It provides no general shell, arbitrary network target, unrelated district access, real process interface, or authority not expressly declared by the card.
