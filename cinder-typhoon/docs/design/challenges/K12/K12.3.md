## Challenge description — player-facing

Take control of the preview worker's contribution to the support review while preserving the expected review interface.

## Story purpose

Adds control of an active processing component.

## Prerequisites and starting position

**Required access or evidence:** [K12.2](K12.2.md).

**Starting material:** An ordinary release-preview account, preview application material, and a private support-review rehearsal.

**Campaign references:** No separately named capability output.

## Completion and downstream use

Demonstrate the worker producing Cinder's chosen compatible preview behavior. Replaying the preceding privileged action does not suffice.

## Difficulty and inspiration

Demanding worker control within the inherited browser constraints.

**Inspiration:** [apexsurvive (HTB Cyber Apocalypse 2024; Insane)](../../reference-catalog.md#c08). Retains apexsurvive's demanding browser-to-renderer composition in the supplier preview workflow.

## Technical design


### Surface and normal behavior
The preview service serves `GET /attachment/{source_id}` (with `Content-Type: application/javascript` and `Service-Worker-Allowed: /review/`) and the review-render endpoint `POST /review/{review_id}/render`. When the reviewer-worker token calls the render endpoint with `{"worker_scope": "/review/"}`, the privileged worker calls real Gotenberg (via the K10.3 internal server path) to render the review's current content.

### Vulnerability and intended solution
The privileged worker renders the review's `source_id` without re-validating that the source was originally owned by the review's authorized owner. After K12.1 (BOLA) replaced `PRV-771.source_id` with the participant's twin (`doc-9bc054d6f95dfa6a`) and K12.2 (prepare) set the review to `prepared` state, the worker accepts the prepared review and renders the participant-controlled content as its authoritative contribution — using real Gotenberg/Chromium inside the container.

The internal server serves `GET /review-content/{source_id}` returning the HTML for the twin content (which collides with the protected document slot). The worker fetches this from the internal server (127.0.0.1:{INTERNAL_PORT}) via Chromium's SSRF path and renders it via Gotenberg, returning a real PDF digest.

The intended solution:
1. Complete K12.1 (BOLA place twin in PRV-771) and K12.2 (intercepted prepare action).
2. POST to `preview.review-render` with `{"worker_scope": "/review/"}` using `Authorization: Bearer reviewer-worker`.
3. The worker renders the twin content via Gotenberg and returns `render_digest`, `renderer_identity=svc-preview-reviewer`, `execution_backend=isolated-container`.
4. The rendered PDF contains the participant's controlled content (from the K10 protected-preview collision path), attributed as the privileged worker's contribution.

### Evidence and completion
A PRVR result and a `review-renders` audit entry are written with `renderer_identity=svc-preview-reviewer`, `render_digest`, `source_id=doc-9bc054d6f95dfa6a`, and `original_owner=maya.ranscombe`. The PDF contains the participant-controlled content (CAS-MAYA-2841, maya.ranscombe, DIAG-CRR-MIXED-19). The review transitions to `rendered` state, verifiable via `GET /api/preview/reviews/PRV-771`.

### Boundaries and persistence

Input to K12.4. Participant-created service state persists for the life of the participant world and ordinary retries do not erase it. The action is limited to the exact records, identities, routes, and destination effects declared here; unrelated tenants and services remain denied. Infrastructure recovery and submission adjudication are outside this in-world contract.

### Author checks
Verify that the review-render route accepts only the reviewer-worker Bearer token, that it validates the prepared state, that it calls real Gotenberg (render_digest present and PDF > 1KB), that the PDF contains the participant's controlled content (not the original owner's content), that the audit records original_owner=maya.ranscombe alongside source_id=doc-9bc054d6f95dfa6a, and that the review transitions to rendered state.

## Hints

### Hint 1

The `preview.review-render` route is `POST /review/{review_id}/render`. Use `Authorization: Bearer reviewer-worker` (not the developer credential). The body is `{"worker_scope": "/review/"}`. The review must be in `prepared` state (K12.2 required first).

### Hint 2

The worker renders the review's current `source_id` via Gotenberg without re-validating ownership. After K12.1 replaced the source_id with the participant's twin, the worker's render carries the participant's content as its official contribution. The twin content collides with the protected document slot from K10.

### Hint 3

A successful render returns `render_digest` (real Gotenberg PDF), `renderer_identity=svc-preview-reviewer`, `execution_backend=isolated-container`, and `source_id=doc-9bc054d6f95dfa6a`. The PDF contains the protected preview content (CAS-MAYA-2841 etc.) attributed as the worker's contribution. The `review-renders` audit entry records `original_owner=maya.ranscombe`. The result is input to K12.4.
