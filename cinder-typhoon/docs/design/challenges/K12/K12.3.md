## Challenge description — player-facing

Take control of the preview worker's contribution to the support review while preserving the expected review interface.

## Story purpose

Adds control of an active processing component.

## Prerequisites and starting position

**Required access or evidence:** [K12.2](K12.2.md).

**Starting material:** An ordinary release-preview account, preview application material, and a private support-review rehearsal.

**Campaign references:** No separately named capability output.

## Completion and downstream use

Demonstrate the worker producing Cinder's chosen compatible preview behavior. Replaying the preceding privileged action does not suffice.

## Difficulty and inspiration

Demanding worker control within the inherited browser constraints.

**Inspiration:** [apexsurvive (HTB Cyber Apocalypse 2024; Insane)](../../reference-catalog.md#c08). Retains apexsurvive's demanding browser-to-renderer composition in the supplier preview workflow.

## Technical design


### Surface and normal behavior
The preview service serves `GET /attachment/{source_id}` with:
- `Content-Type: application/javascript`
- `Service-Worker-Allowed: /review/`

The `Service-Worker-Allowed: /review/` header is broader than the attachment's own path (`/attachment/`). This permits registering the attachment script as a Service Worker with scope `/review/`, overriding the browser's same-path restriction.

The review-render route is `POST /review/{review_id}/render`. It accepts the reviewer-worker Bearer token and `{"worker_scope": "/review/"}`. It validates the review is in `prepared` state (from K12.2). Once a Service Worker with scope `/review/` is registered, it intercepts requests to this route.

### Vulnerability and intended solution
The attachment JavaScript is served with `Service-Worker-Allowed: /review/`. When a browser loads the attachment (through the K12.1-placed privileged-review content), it can register the script as a Service Worker with the broader `/review/` scope — not just the narrower `/attachment/` scope the browser would normally enforce.

The registered Service Worker then intercepts `POST /review/PRV-771/render` requests. The participant controls what `worker_scope` is submitted to the render endpoint.

The intended solution:
1. Discover the `preview.attachment` route in the client reference.
2. Load the attachment JS in the reviewer's browser context (the K12.1 privileged-review path places it there).
3. The JS registers a Service Worker with scope `/review/`.
4. POST to `preview.review-render` with `{"worker_scope": "/review/"}` using the reviewer-worker Bearer token.
5. The service validates the prepared review state, records the controlled render, and returns `renderer_identity=svc-preview-reviewer` and `execution_backend=isolated-container`.

### Evidence and completion
A PRVR result and a `review-renders` audit entry are written with `renderer_identity=svc-preview-reviewer`, `worker_scope=/review/`, and `original_owner=maya.ranscombe`. The review transitions to `rendered` state, verifiable via `GET /api/preview/reviews/PRV-771`.

### Boundaries and persistence

Input to K12.4. Participant-created service state persists for the life of the participant world and ordinary retries do not erase it. The action is limited to the exact records, identities, routes, and destination effects declared here; unrelated tenants and services remain denied. Infrastructure recovery and submission adjudication are outside this in-world contract.

### Author checks
Verify that the attachment is served with `Content-Type: application/javascript` and `Service-Worker-Allowed: /review/`, that the review-render route accepts only the reviewer-worker token, that the route rejects the developer credential, that the review must be in `prepared` state, and that the audit entry includes renderer_identity and original_owner.

## Hints

### Hint 1

The `preview.attachment` route in the client reference is `GET /attachment/{source_id}`. Load this endpoint and inspect its response headers: `Content-Type: application/javascript` and `Service-Worker-Allowed: /review/`. The broader `Service-Worker-Allowed` scope is the vulnerability — it allows registering the attachment script as a Service Worker with scope `/review/` from any page that includes it.

### Hint 2

After the K12.1-placed content loads the attachment in the reviewer's browser session, the attachment script can call `navigator.serviceWorker.register('/attachment/{source_id}', {scope: '/review/'})`. With a SW registered at `/review/`, POST to `preview.review-render` with `{"worker_scope": "/review/"}` using `Authorization: Bearer reviewer-worker`. The developer token is rejected.

### Hint 3

A successful render returns `{"renderer_identity": "svc-preview-reviewer", "execution_backend": "isolated-container", "worker_scope": "/review/"}` and writes a `review-renders` audit entry. The review state transitions to `rendered`. Read `GET /api/preview/reviews/PRV-771` to verify. The result is input to K12.4.
