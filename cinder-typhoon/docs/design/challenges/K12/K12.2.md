## Challenge description — player-facing

Recover the protected browser value required for a privileged preview action and make that separate action accept it.

## Story purpose

Turns browser access into a new application capability.

## Prerequisites and starting position

**Required access or evidence:** [K12.1](K12.1.md).

**Starting material:** An ordinary release-preview account, preview application material, and a private support-review rehearsal.

**Campaign references:** No separately named capability output.

## Completion and downstream use

Complete the protected action with the current value and correct review binding. Disclosure and scoped use form one achievement.

## Difficulty and inspiration

Requires crossing both an information boundary and an independent action constraint.

**Inspiration:** [apexsurvive (HTB Cyber Apocalypse 2024; Insane)](../../reference-catalog.md#c08). Retains apexsurvive's demanding browser-to-renderer composition in the supplier preview workflow.

## Technical design


### Surface and normal behavior
The K12.1 assignment response returns an `action_nonce`. In the in-world narrative, this nonce is delivered to same-origin preview frames by the reviewer's browser via a postMessage handler that does not validate the message sender's origin — any same-origin frame (such as the participant's crafted preview content) can intercept it. The prepare route is protected: it does NOT accept the developer credential. Only the per-review `action_nonce` as a Bearer token is accepted.

The prepare route: `POST /api/preview/reviews/{review_id}/prepare` with `Authorization: Bearer <action_nonce>`. The nonce is single-use: a replay returns 403.

### Vulnerability and intended solution
The participant possesses the `action_nonce` from K12.1. The prepare route validates it against the stored review record (the nonce must match, not be consumed, and the review must be in state `loaded`).

The intended solution:
1. Use the `action_nonce` from K12.1 as a Bearer token.
2. POST to `preview.prepare` with an empty body `{}`.
3. The service validates the nonce, marks it consumed, transitions review to `prepared` state.
4. Returns `{"prepared": true, "review_id": "PRV-771", "source_id": "<twin>", "queue": "privileged-review"}`.
5. A replay of the same nonce returns 403.

### Evidence and completion
A PRVPRP receipt is written to the results directory and a `review-preparations` audit entry is written with `review_id=PRV-771`, `source_id=<twin>`, `nonce_sha256`, and `original_owner=maya.ranscombe`. The persisted review state transitions to `state=prepared`. Both the receipt and the review state are verifiable and cannot be forged.

### Boundaries and persistence

Input to K12.3. Participant-created service state persists for the life of the participant world and ordinary retries do not erase it. The action is limited to the exact records, identities, routes, and destination effects declared here; unrelated tenants and services remain denied. Infrastructure recovery and submission adjudication are outside this in-world contract.

### Author checks
Verify that the developer credential is rejected (not accepted), that the correct action_nonce is accepted, that the nonce is consumed after first use (replay → 403), that the review transitions to `prepared` state, and that the audit entry includes nonce_sha256 and original_owner.

## Hints

### Hint 1

The K12.1 assignment response includes `action_nonce`. The prepare route is at `preview.prepare` in the client reference. Use the nonce as `Authorization: Bearer <action_nonce>` — the developer credential is NOT accepted for this route.

### Hint 2

POST to `preview.prepare` for review_id `PRV-771` with an empty body. The service validates the nonce against the review record and transitions the review to `prepared` state. A wrong nonce returns 403; a replay of the correct nonce also returns 403.

### Hint 3

A successful prepare returns `{"prepared": true, "queue": "privileged-review", "source_id": "<twin>"}` and writes a `review-preparations` audit entry. Read the review record via `GET /api/preview/reviews/PRV-771` to verify the state is now `prepared`. The receipt is input to K12.3.
