## Challenge description — player-facing

Establish the limited workload identity available from this workspace and recover the protected record within its actual scope.

## Story purpose

Makes cloud identity a demonstrated capability rather than a found label.

**Starting material:** The cloud workspace notebook, object references, export notes, and ordinary developer-visible workload records.

**Campaign references:** No separately named capability output.

## Completion and downstream use

Recover the protected workload record using the available identity. This supplies authenticated starting context for K14, K15, and K30. K31 requires the further scoped role from K14.2, or the separate K09.4 job-execution route.

## Technical design


### Surface and normal behavior
`k-cloud-api` is a thin Python service on the cloud network. It proxies two operations to real K3s:
1. `POST /api/workspaces/current/token-exchange` (developer credentials) → calls the K3s TokenRequest API → returns a real short-lived service-account token for `svc-fieldlink-workload`.
2. `GET /api/build-records/{build_id}` (SA token from step 1) → calls the K3s ConfigMap API with the participant's SA token; K3s RBAC enforces scope.

The protected record is a real Kubernetes ConfigMap `bld-1842` in the `fieldlink` namespace. The ServiceAccount `svc-fieldlink-workload` has a RoleBinding granting it GET access to `bld-1842` only. Reading any other ConfigMap → K3s returns 403.

### Vulnerability and intended solution
The workspace token exchange is accessible with developer credentials, allowing the participant to obtain a real K3s workload identity for `svc-fieldlink-workload`. The scope is enforced by real K3s RBAC, not by the Python service.

The intended solution:
1. `GET /api/workspaces/current/token-exchange` (developer credentials) → workspace exchange info.
2. `POST /api/workspaces/current/token-exchange` (developer credentials, body `{}`) → real K3s SA token for `svc-fieldlink-workload`.
3. `GET /api/build-records/BLD-1842` (Bearer SA token) → cloud-api forwards to K3s ConfigMap; RBAC allows; returns BLD-1842 data with `principal=svc-fieldlink-workload`.
4. Attempting to read any other ConfigMap → K3s returns 403 (genuine RBAC enforcement).

### Evidence and completion
The SA token is a real K3s TokenRequest token (JWT from K3s). The BLD-1842 response has `principal=svc-fieldlink-workload`. An out-of-scope read returns `k3s_rbac_denied`. Both the token issuance and the ConfigMap read are audited by k-cloud-api.

### Boundaries and persistence

Usable starting identity for K14/K15/K30. Participant-created service state persists for the life of the participant world and ordinary retries do not erase it. The action is limited to the exact records, identities, routes, and destination effects declared here; unrelated tenants and services remain denied. Infrastructure recovery and submission adjudication are outside this in-world contract.

### Author checks
Verify that the SA token is a real K3s JWT (not a random string), that BLD-1842 is a real K3s ConfigMap, that the RBAC Role only allows GET on `bld-1842`, that reading another ConfigMap returns 403 from K3s, and that the developer token cannot directly read the build record (only the SA token can).

## Hints

### Hint 1

Call `GET /api/workspaces/current/token-exchange` (developer credentials) to get workspace info. Then `POST /api/workspaces/current/token-exchange` with body `{}` to receive a real K3s service-account token for `svc-fieldlink-workload`. The token is short-lived (1 hour).

### Hint 2

Use the SA token as `Authorization: Bearer <token>` to call `GET /api/build-records/BLD-1842`. The cloud-api forwards the request to K3s ConfigMap API using your SA token — K3s RBAC allows the read because svc-fieldlink-workload has GET access to bld-1842 only. The response contains `principal=svc-fieldlink-workload`.

### Hint 3

The SA token is scoped by real K3s RBAC. Reading any other build record or ConfigMap returns `k3s_rbac_denied`. The result `principal=svc-fieldlink-workload` and the K3s token (a real JWT) are the K13.4 completion evidence. Keep the SA token for K14, K15, and K30.
