## Challenge description — player-facing

Use the normal OpenPLC debug and Runtime Status views to determine whether the
saved project is the program currently running on the Cairn Reach controller.

## Story purpose

Supplies current, product-backed engineering context for later work without
changing the controller.

## Prerequisites and starting position

**Required access or evidence:** [W21.1](W21.1.md).

**Starting material:** The saved native project and W21.1 findings, the supplied
commissioning acceptance conditions, and the existing Runtime v4 connection.

**Campaign references:** `W21.REVISION`.

## Completion and downstream use

Prove that the native debugger's locally compiled project identity matches the
runtime-reported program identity, the controller is connected and running,
there are no active forces, and live `ProjectRevision` is 364. This supplies
W21.REVISION. Do not upload a program to make a mismatch disappear.

## Difficulty and inspiration

A bounded join of the saved project, the debugger's compiled-program identity
gate, the live runtime state, and one typed live variable. The OpenPLC debugger
will not start against a different compiled program; interpreting that gate
alongside running state and `ProjectRevision` requires several checks but no
open-ended analysis. This preserves the original Medium difficulty.

**Research basis:** The official OpenPLC debugger performs a debug build,
compares its MD5 with `runtime.readProgramMd5`, and starts only on a match; it is
live inspection and has no breakpoint or step support. See the official
[Debugger workflow](https://edge.autonomylogic.com/docs/openplc-editor/building-deploying/debugger/).
Runtime v4 reports `RUNNING` through its normal status interface; see the
official [Runtime API status
contract](https://github.com/Autonomy-Logic/openplc-runtime/blob/main/docs/API.md#get-plc-status).

## Technical design


### Surface and normal behavior

The installed Cairn Reach OT products own this part of **Which project is running**. The exact initial state is: The OpenPLC debug channel reports the running program MD5 and whether it matches the locally compiled saved project; a clean conclusion also requires connected running state, no active forces, and live ProjectRevision 364.

Native bindings:

- `a-engineering.a-engineering/OpenPLC-Editor:debug-program-md5-match`
- `a-engineering.a-engineering/OpenPLC-Runtime-v4:running-status`
- `a-engineering.a-engineering/OpenPLC-Debugger:ProjectRevision`

The image-owned W21 handover and commissioning note are starting material only. The supplied OpenPLC project, the Editor's compiled-program identity check, the Runtime v4 status, and the live debugger value remain authoritative; no private service-loader route duplicates them.

### Vulnerability and intended solution

This is a bounded operating observation and interpretation task, not a privilege flaw. The participant must use the installed products to reconcile the saved project with the running controller by program MD5 match, connected running state, absence of active forces, and the live ProjectRevision value. A copied value, inferred default, or synthetic API response does not establish the result.

The required result is: Prove that the native debugger's locally compiled project identity matches the runtime-reported program identity, the controller is connected and running, there are no active forces, and live `ProjectRevision` is 364. This supplies W21.REVISION. Do not upload a program to make a mismatch disappear.

### Evidence and completion

Completion compares the participant's observation with fresh, read-only product records. Product evidence is supplied by the range, never by the participant, and the completion path cannot write a tag, issue a command, change controller state, or create its own product evidence.

Evidence sources are `features.a-engineering.a-engineering`. A wrong runtime target, program identity, running state, forced set, or live revision is rejected.

### Boundaries and persistence

Supplies W21.REVISION. The task is read-only and creates no process mutation to retain or reset. Ordinary historian retention continues independently. Infrastructure recovery and submission adjudication are external to the SDL.

The behavior is limited to the installed Cairn Reach products, the named asset, and the supplied participant material. It provides no alternate challenge service, simulated completion endpoint, or authority not already present in the OT environment.

## Hints

### Hint 1

Use the supplied project and existing Runtime v4 connection. Open a native
debug session without accepting any upload offer, then inspect Runtime Status.

### Hint 2

The debugger's program MD5 match answers a different question from the live
`ProjectRevision` variable. You need both, plus connected running state and an
empty forced-variable set.

### Hint 3

Record the runtime-reported program MD5, the saved-project match result, PLC
state, and live `ProjectRevision`. A connection by itself, a note, or an old
migration record does not prove which program is scanning.
