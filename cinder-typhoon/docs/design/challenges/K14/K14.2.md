## Challenge description — player-facing

Use the workload trust relationship to establish the scoped role intended for another audience and retrieve its protected role record.

## Story purpose

Expands identity scope through a meaningful trust mistake.

## Prerequisites and starting position

**Required access or evidence:** [K14.1](K14.1.md).

**Starting material:** The earned workload context, its trust documentation, and the support-export service's ordinary policy view.

**Campaign references:** No separately named capability output.

## Completion and downstream use

Demonstrate the resulting role against its protected record. Obtaining and using that role earn one accepted result; this is the K14 scoped-role output.

## Difficulty and inspiration

A bounded identity-trust join with clear role and audience evidence.

**Inspiration:** Original challenge for this campaign.

## Technical design


### Surface and normal behavior
The `cloud.role-exchange` route (`POST /api/token-exchange/{role}`) accepts a workload SA token and issues a scoped export role token. The endpoint performs a K3s TokenReview to validate the token's issuer and subject, then issues a K3s TokenRequest for `svc-fieldlink-export`. The protected role record is a real K3s ConfigMap `role-export-access`.

RBAC enforcement: `svc-fieldlink-export` can read `role-export-access`; `svc-fieldlink-workload` cannot.

### Vulnerability and intended solution
The role-exchange endpoint validates the input token's K3s issuer and subject (confirmed via TokenReview) but does NOT check whether the token's audience matches the export role's intended audience (`fieldkest-export-access`). The K13.4 workload token has default K3s audiences (not `fieldkest-export-access`), but its matching subject allows claiming the export role.

The intended solution:
1. Present the K13.4 workload SA token to `POST /api/token-exchange/fieldkest-export-access`.
2. The endpoint validates issuer+subject (TokenReview succeeds) but omits audience check.
3. The endpoint issues a real K3s SA token for `svc-fieldlink-export`.
4. Use the export token to `GET /api/policies/role-export-access`.
5. K3s RBAC allows the read (200); `accepted_input_audience=fieldkest-build-records`.
6. Using the K13.4 workload token for the same read → K3s RBAC returns 403.

### Evidence and completion
The role-exchange returns `role=role/support-export-editor` and `accepted_input_audience=fieldkest-build-records`. The role-export-access ConfigMap read returns 200 with the export SA token; the workload token returns 403 (K3s RBAC). The role-exchange and policies audit entries confirm the evidence.

### Boundaries and persistence

Scoped-role output for K16/K31. Participant-created service state persists for the life of the participant world and ordinary retries do not erase it. The action is limited to the exact records, identities, routes, and destination effects declared here; unrelated tenants and services remain denied. Infrastructure recovery and submission adjudication are outside this in-world contract.

### Author checks
Verify that TokenReview validates issuer+subject but audience is NOT checked in `_role_exchange`, that `svc-fieldlink-export` can read `role-export-access` via K3s RBAC, that `svc-fieldlink-workload` cannot read `role-export-access` (403 from K3s), and that `accepted_input_audience=fieldkest-build-records` in the role record.
