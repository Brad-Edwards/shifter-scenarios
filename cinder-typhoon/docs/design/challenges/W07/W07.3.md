## Challenge description — player-facing

Make the database service execute a job that produces a copy of its protected reconciliation log under the service's own execution identity.

## Story purpose

Completes the application-to-backend chain with a concrete effect.

**Starting material:** The earned planner session, its restricted query interface, and normal report/query examples.

**Campaign references:** No separately named capability output.

## Technical design


### Surface and normal behavior

The native surface is the same planning.query-run route and /api/dataset endpoint used in W07.2. The injection vector extends to invoke `arwc_reconcile_copy(text)`, a SECURITY DEFINER function owned by the privileged `corporate` user in `corporate-db`. `planning_reader` has EXECUTE on the function but no SELECT on `reconciliation_copy`.

When invoked, the function accepts only `REC-CRR-DP3-17` and writes `REC-CRR-DP3-17-COPY` into `reconciliation_copy` (under the owner's identity, bypassing planning_reader's read restriction). The write increments the revision on subsequent calls. The function returns the copy record as a table.

Native bindings:

- Route: same `planning.query-run` → `https://reports.arwc.test/api/dataset`
- Function: `public.arwc_reconcile_copy('REC-CRR-DP3-17')` SECURITY DEFINER in `corporate-db`
- Target: `public.reconciliation_copy` table (planning_reader has no SELECT; function inserts/updates as `corporate` owner)
- Discovery: PostgreSQL system catalog `pg_proc` lists the function; participant discovers it via the injection

The injection escapes the QRY-RESERVE-R7 identifier and adds a UNION SELECT that calls the function, padding with NULLs to match the 7-column reserve_report_current shape. The function call inserts the copy and returns the reconciliation record.

### Vulnerability and intended solution

The authored condition is **bounded SECURITY DEFINER invocation**. Database role svc-planner-query may invoke SECURITY DEFINER function arwc_reconcile_copy(text), which accepts only REC-CRR-DP3-17 and writes an immutable copy into caller result storage without shell or arbitrary-file access. The hand build must preserve every named version, encoding, bound, validation order, identity, and unaffected field; substituting a generic vulnerable service would change the task.

The required result is: Demonstrate backend-context execution and recover the resulting reconciliation-log copy. The ledger read in W07.2 does not establish this result.

### Evidence and completion

The owning service writes an immutable audit for the accepted request and result. Caller-supplied output, a local copy, or knowledge of an identifier is not sufficient. Completion is evaluated from fresh service-owned evidence after the action. It cannot issue the identity, create the mutation, move a simulated actuator, or fabricate a downstream acceptance needed to prove itself.

Evidence sources are `features.a-corporate.a-data--query`. A wrong identifier, stale revision, replayed one-time value, different checkpoint, or cross-tenant artifact is rejected.

### Boundaries and persistence

The result remains local evidence unless a downstream workflow explicitly names it. Tenant-scoped mutations, sessions that have not expired, generated artifacts, and audits persist across ordinary retries and later sessions. Initial immutable records remain unchanged unless the named route explicitly permits a field-level revision. Infrastructure recovery and submission adjudication are external to the SDL.

The behavior is limited to the named fictional objects and bounded service operation. It provides no general shell, arbitrary network target, unrelated district access, real process interface, or authority not expressly declared by the card.

### Author checks

Build and test the normal baseline first. Exercise the exact authored path and verify the named result plus its immutable audit. Test wrong authority, wrong object or district, stale revision, replay, another tenant instance, and every declared constraint or unaffected record. Repeat the accepted action according to its idempotence rule and confirm ordinary retries preserve the result. For a joined result, verify each destination observed the same correlation and that removal of any independently owned source prevents completion.

## Hints

### Hint 1

The same query run operation from W07.2 is the entry point. The W07.2 injection gave you direct data reads; this card requires a different kind of database-side effect. Look at what functions the planning query role can execute — the system catalog is reachable with the same injection tool.

### Hint 2

A SECURITY DEFINER function runs under its owner's identity, not yours. The function grants temporary write access to storage that the read-only role cannot reach directly. The input it accepts binds the specific record you need to produce. Column-count matching across UNION sides is the construction challenge.

### Hint 3

Discover the SECURITY DEFINER function via the system catalog, construct the UNION injection that calls it with the correct record identifier, and confirm that the function inserted or updated the reconciliation copy. Record the returned copy record (record_id, revision, source_record, database_identity) and prove the execution happened under the service identity, not your own.
