## Challenge description—player-facing

Cross the check-in service's separate identity boundary and establish the contractor session for the correct inspection scope.

## Story purpose

Completes the alternative contractor route's identity stage.

## Prerequisites and starting position

**Required access or evidence:** W13.3 (appointment attendee updated to veybridge.tech.204).

**Starting material:** The updated appointment from W13.3, the roster from W13.2, and the `contractors.check-in` route in the contractor portal client document.

**Campaign references:** W13.SESSION.

## Completion and downstream use

Demonstrate the scoped contractor session against its protected field-work record. The contractor session is a real ERPNext-issued session ID (`field-work:read` scope), not a canned token. This supplies W13.SESSION.

## Difficulty and inspiration

A small credential-issuance and assignment-binding problem.

**Inspiration:** Original challenge for this campaign.

## Technical design

### Surface and normal behavior

The `contractors.check-in` route → POST `contractor-portal.arwc.test/api/check-ins`.

The request requires:
- `appointment_id`: APT-CRR-2026-09-18
- `roster_id`: the roster record ID from W13.2 (ROSTER-CRR-SEP18-R2)
- `identity`: the contractor identity from the roster (veybridge.tech.204)

**Validation:** The service checks that:
- The appointment_id matches the current appointment
- The roster_id matches the current roster
- The identity matches the roster identity
- The current appointment attendee equals the roster identity (set by W13.3 BOLA)

**Real authentication:** On a successful check-in, the portal obtains a real ERPNext session token by logging into `suppliers.arwc.test` with operator credentials. The session ID (a 56-char hex string genuinely issued by ERPNext) is used as the contractor session bearer token. The token hash is stored in service state; the token itself is stored in the HANDOVER file for downstream use.

**Session scope:** `SCOPE-INSP-CRR-4417`, inspection=INSP-CRR-2026-09-18, asset=AST-CRR-017, identity=veybridge.tech.204, assignment=CTR-VEY-204, scope=field-work:read.

The contractor session is then used to access `/api/field-kits/current` (the protected field-work record).

Native bindings:

- Route: `contractors.check-in` → POST `contractor-portal.arwc.test/api/check-ins`
- Real authentication: ERPNext session via `suppliers.arwc.test/api/method/login`
- Protected resource: `contractors.field-kit` → GET `contractor-portal.arwc.test/api/field-kits/current`

### Vulnerability and intended solution

The authored condition is **attendee-derived session issuance**. The check-in service trusts the current appointment attendee and roster identity—both of which were manipulated by the W13.3 BOLA. The W13.4 check-in accepts the participant's identity because the BOLA already registered it as the appointment attendee. The session issued is a real ERPNext-authenticated token with field-work:read scope.

The participant:
1. Uses appointment_id and roster_id from W13.1/W13.2
2. Supplies identity=veybridge.tech.204 (the roster identity set by W13.3)
3. Receives a real ERPNext session ID as the contractor session
4. Uses the session to access the protected field-work record (FIELD-BAG-CRR-4417-R3)

### Evidence and completion

The archive service writes an immutable audit (`contractor-check-in-created`). The returned session allows access to the protected field-work record. Evidence sources are `features.a-maintenance.a-contractors`.

### Boundaries and persistence

The contractor session persists in the HANDOVER file across restarts. The session is single-issue per check-in. Field-kit access requires a valid contractor session.

### Author checks

Verify check-in with correct appointment/roster/identity succeeds and returns a 56-char hex ERPNext session. Test wrong roster_id (403). Verify field-kit returns FIELD-BAG-CRR-4417-R3 with the contractor session. Verify the session is from ERPNext (hex string, not base64 random).

## Hints

### Hint 1

The contractors.check-in route requires the appointment_id from W13.1, the roster_id from W13.2, and the identity (veybridge.tech.204) from the W13.2 roster. The W13.3 BOLA already set the appointment attendee to match your identity, so the check-in service accepts it.

### Hint 2

After a successful check-in, the returned contractor_session is a real ERPNext-issued session token. Use it as a bearer token to call contractors.field-kit—this is the protected field-work record for the inspection scope.

### Hint 3

The field-kit record (FIELD-BAG-CRR-4417-R3) names the expected outlets and service manifest for the inspection. The contractor session scope is field-work:read, which is the minimum needed for the downstream W14+ cards. Record the contractor_session value from the check-in response.
