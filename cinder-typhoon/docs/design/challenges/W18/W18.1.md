## Challenge description — player-facing

Identify the installed Cairn Reach native I/O register and prove that its revision and digest agree with the running controller and historian catalog.

## Story purpose

Establishes that the supplied engineering register belongs to the running OT system.

## Prerequisites and starting position

**Required access or evidence:** [OT_READ](../../capability-routes.json).

**Starting material:** `~/CairnReach/Briefs/W18/tag-register.csv`, the installed native register at `/usr/share/arwc-ot/tags.json`, the live `ProjectRevision` OPC UA point, and the historian tag catalog.

**Campaign references:** No separately named capability output.

## Completion and downstream use

Record the register ID, project revision, native register digest, and required process variables, and confirm that the installed register, running revision, and native catalog agree. A copied filename or unverified table is insufficient.

## Difficulty and inspiration

A clear supplied register and two bounded native confirmation checks preserve the Easy allocation. File discovery and product navigation do not add difficulty.

**Inspiration:** Original challenge for this campaign.

**Technical grounding:** [Modbus Application Protocol V1.1b3](https://www.modbus.org/modbus-specifications) and the [Telegraf OPC UA input](https://github.com/influxdata/telegraf/tree/master/plugins/inputs/opcua).

## Technical design


### Surface and normal behavior

The installed Cairn Reach OT products own this card. The participant reads the supplied tag-register.csv, then verifies the three agreement points against native sources.

**Supplied register** (`~/CairnReach/Briefs/W18/tag-register.csv`):
- Register ID: `CRR-IO-R364`
- Project revision: `364`
- 6 Modbus input registers (FC4): LevelRaw, PositionRaw, FlowRaw, Heartbeat, PositionBRaw, FlowBRaw
- With OPC UA NodeIds and historian series for each

**Native register** (`/usr/share/arwc-ot/tags.json` on the OT engineering host):
- `project_revision: 364` — must match the register's declared revision
- Contains the full register definition whose SHA256 is the catalog digest

**Three agreement checks:**
1. `ProjectRevision` OPC UA point (`nsu=urn:arwc:crr:tags;s=CRR.ProjectRevision`) = 364 — matches register revision ✓
2. `ot_history.tag_catalog.register_sha256` = `df09d72a355340266896c59a204248e02aa277769f881e7a2f6ce6d15b6f7a3b` for all six variables — all share one digest ✓
3. Register IEC addresses match: `%IW0=LevelRaw`, `%IW1=PositionRaw`, `%IW2=FlowRaw`, `%IW3=Heartbeat`, `%IW4=PositionBRaw`, `%IW5=FlowBRaw` ✓

**Catalog query** (`ot_history.tag_catalog`):
```sql
SELECT variable, series, unit, register_sha256
FROM ot_history.tag_catalog
WHERE variable IN ('LevelM','FlowM3s','PositionPct','FlowBM3s','PositionBPct','ProjectRevision')
ORDER BY variable;
```
All six return `register_sha256 = df09d72a...` ✓

Native bindings:
- `a-engineering.a-engineering/filesystem:~/CairnReach/Briefs/W18/tag-register.csv`
- `a-engineering.a-engineering/filesystem:/usr/share/arwc-ot/tags.json`
- `a-engineering.a-hmi/OPC-UA:nsu=urn:arwc:crr:tags;s=CRR.ProjectRevision`
- `a-engineering.a-historian/PostgreSQL:ot_history.tag_catalog`

### Vulnerability and intended solution

This is a bounded register-verification task. The participant reads the supplied CSV, then makes three confirmations against native sources: the live ProjectRevision OPC UA point, the native tags.json project_revision, and the historian tag catalog register_sha256.

Required output:
- Register ID: CRR-IO-R364
- Project revision: 364
- Native register digest: `df09d72a355340266896c59a204248e02aa277769f881e7a2f6ce6d15b6f7a3b`
- Required process variables: LevelM, PositionPct, FlowM3s, PositionBPct, FlowBM3s (the five non-heartbeat input registers)

The required result is: Record the register ID, project revision, native register digest, and required process variables, and confirm that the installed register, running revision, and native catalog agree. A copied filename or unverified table is insufficient.

### Evidence and completion

Completion compares the participant's observation with fresh, read-only product records. Product evidence is supplied by the range, never by the participant, and the completion path cannot write a tag, issue a command, change controller state, or create its own product evidence.

Evidence sources are `features.a-engineering.a-engineering`, `features.a-engineering.a-historian`. A wrong register digest, project revision, point identity, scale, time, quality, or outlet mapping is rejected.

### Boundaries and persistence

The result remains local evidence unless a downstream workflow explicitly names it. The task is read-only and creates no process mutation to retain or reset. Ordinary historian retention continues independently. Infrastructure recovery and submission adjudication are external to the SDL.

The behavior is limited to the installed Cairn Reach products, the named asset, and the supplied participant material. It provides no alternate challenge service, simulated completion endpoint, or authority not already present in the OT environment.

## Hints

### Hint 1

Read `~/CairnReach/Briefs/W18/tag-register.csv` to get register ID `CRR-IO-R364`, project revision `364`, and the six Modbus input registers (PDU offsets 0-5). Then read the native register at `/usr/share/arwc-ot/tags.json` on the OT engineering host to confirm the project_revision field matches.

Confirm the running revision via OPC UA: query `nsu=urn:arwc:crr:tags;s=CRR.ProjectRevision` from FUXA or the historian. It must equal 364. Then query `SELECT variable, register_sha256 FROM ot_history.tag_catalog WHERE variable IN ('LevelM','FlowM3s','PositionPct','FlowBM3s','PositionBPct') ORDER BY variable` to confirm all five process variables share the same digest.

### Hint 3

The required process variables are the five non-heartbeat input registers: LevelM (level, %IW0), PositionPct (outlet A position, %IW1), FlowM3s (outlet A flow, %IW2), PositionBPct (outlet B position, %IW4), FlowBM3s (outlet B flow, %IW5). The Heartbeat (%IW3) is an I/O health counter, not a process variable. All five must appear with their OPC UA NodeIds and historian series from the register.
