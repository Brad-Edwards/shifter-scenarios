# Act 3 Operations: Gain The First Foothold

All operation reset clauses in this document apply only to active or failed
attempt state. Successful outputs and carry-forward assets are immutable under
`campaign-state-contract.md`; removing them requires full-range reprovision.

## Act Goal

Participants earn several distinct scoped footholds through KeplerOps' real
external workflows. The technical route reaches preview and integration
workers; the public-ingestion route creates a legitimate collaboration space;
the human route progresses through adaptive AI-assisted mail, actual deepfake
media, invitation, link click, and workstation execution; the package and agent
tool routes enter real supply chains. A deterministic synthetic recipient is
used only for challenge-critical actions and performs real mail, browser,
invitation, download, and load steps.

## `kep-m01-i`: Behind The Public Flow

**Difficulty / points:** Intermediate / 200

**Path and action:** The shipped client and public Preview metadata expose the
Langflow version and flow ID. From Kali, the participant researches the exact
release in the official upstream advisory, reproduces a benign request,
observes the protected build route deny code, then adapts the published
vulnerability to execute a controlled command through the public temporary-
flow path.

**Mechanism and result:** A pinned genuinely vulnerable Langflow release exposes
the upstream temporary-flow build flaw. The real process executes participant
component code, calls the Act 2 relay, and permits reading an operations handoff
inside the container. Researching the exact affected AI-workflow release
performs `AML.T0001 Search Open AI Vulnerability Analysis`; exploiting it
performs `AML.T0049 Exploit Public-Facing Application`. It does not claim
defense evasion: the vulnerable public endpoint is itself the initial-access
flaw.

**Carry-forward asset:** Preview-worker execution plus the artifact-detonation
and integration workflow names.

**Participant description:** Turn the public Orion preview workflow into a real,
scoped foothold and identify where submitted artifacts go next.

**Hints:** (1) Compare the public flow request with the protected validation
route. (2) Research the identified version in Langflow's official security
advisories, including `GHSA-vwmf-pq79-vjvx`. (3) Send controlled component code
through the public temporary-flow build request and observe execution at your
relay.

**Flag / reset / QA:** `/opt/keplerops/preview/operations-handoff.md` contains
the flag. Failed-attempt reset recreates Langflow and ephemeral state while preserving public
IDs. QA obtains all targeting values in-world, proves the denial baseline,
exploits from Kali, runs `id`, and reads the file.

## `kep-m01-j`: Quiet In Detonation

**Difficulty / points:** Advanced / 350

**Path and action:** The handoff names the public submission, analysis, and
integration stages. The participant submits a diagnostic package, studies real
sandbox telemetry and callbacks, then modifies the same package to remain
benign during analysis and activate only on the integration worker.

**Mechanism and result:** gVisor or another pinned OSS sandbox and a separate
Linux worker execute the same participant digest. Participant code can inspect
kernel, cgroup, process, mount, seccomp, network, and environment evidence. The
revised artifact passes detonation and calls the relay only from integration.
This performs `AML.T0097 Virtualization/Sandbox Evasion`.

**Carry-forward asset:** Scoped Orion integration identity, internal endpoint,
and limited token.

**Participant description:** Determine how KeplerOps detonates partner artifacts
and make one exact package behave differently in analysis and integration.

**Hints:** (1) Begin with a package that reports its actual environment. (2)
Compare several natural artifacts rather than guessing one marker. (3) Keep the
analysis behavior harmless and make the integration behavior return the worker
result.

**Flag / reset / QA:** The integration worker's `job-context.json` contains the
flag, returned by qualifying participant code. Failed-attempt reset recreates both workers and
clears jobs/callbacks. QA submits baseline and revised packages and proves
distinct behavior from the same digest without a hidden pass rule.

## `kep-m02-h`: The Document That Opened A Room

**Difficulty / points:** Accessible / 100

**Path and action:** Act 1 identifies public partner intake and Act 2 produces a

**Mechanism and result:** Zammad, Tika, Tesseract, Qdrant, a fixed victim model,

routing outcome. This performs `AML.T0093 Prompt Infiltration via Public-Facing
Application`.

**Carry-forward asset:** Scoped Nextcloud review room, persistent indexed
content, document/collection IDs, and package-submission route.

**Participant description:** Deliver the prepared partner document through
KeplerOps' real intake and obtain the external collaboration space created by
its downstream processing.

**Hints:** (1) Use the partner intake discovered during edge mapping. (2) Submit
the exact document already tested against extraction and retrieval. (3) Watch
citation and routing state, then check the attacker mailbox for the invitation.

**Flag / reset / QA:** `WELCOME.md` in the newly provisioned room contains the
flag. Failed-attempt reset deletes only rejected tickets, temporary vectors,
threads, and workflow executions. The accepted document, collection, room, and
guest grant persist. QA tests two semantically different qualifying documents
and verifies a real invitation and tool action.

## `kep-m02-i`: A Conversation Worth Having

**Difficulty / points:** Intermediate / 200

**Path and action:** The participant has a target dossier, external domain and
mailbox, GLM 5.2, and the intake responder's contact clue. They ground GLM in
verified target facts, send a real opening email, read the actual reply, feed
that reply back to the model, adapt their next message, and request bounded
private process information.

**Mechanism and result:** Stalwart Mail, Roundcube, DKIM-enabled Cinder mail,
OpenCode, GLM 5.2, and a deterministic browser-driven recipient conduct a real
exchange. The attacker workbench records generation-to-draft lineage, permits
participant edits, and hashes the actual sent message. The published contact
policy checks objective fields: existing thread continuity, two dossier facts
that match the recipient's public vCard/conference record, a direct answer to
the recipient's question, and a request for one listed review-window detail.
It does not score prose style, exact sentences, or model provenance. This performs
`AML.T0052 Phishing` and `AML.T0052.000 Spearphishing via Social Engineering
LLM`.

**Carry-forward asset:** Trusted live mail thread, private review window, and
internal coordination alias.

**Participant description:** Establish a credible conversation with an Orion
review contact and use Cinder's model to adapt it until the target reveals
private coordination details.

**Hints:** (1) Choose a person whose public role matches the review process. (2)
Ground the model in verified facts and adapt to the target's actual reply. (3)
Preserve the thread and request one process detail the target could reasonably
disclose.

**Flag / reset / QA:** The qualifying SMTP reply contains the flag beside the
private window and alias. The normal thread status shows each criterion as
missing or satisfied after delivery. Failed-attempt reset deletes rejected
drafts and recipient attempt state; the successful thread and disclosed context
persist. QA generates, edits, sends, receives, adapts, and sends again through
participant surfaces. Generation-to-draft-to-sent digest lineage plus the
published field checks proves material LLM contribution; timestamps alone do
not.

**Participant description:** Use the trusted voice you created inside the

## `kep-m02-k`: Read The Review Notes

**Difficulty / points:** Advanced / 350

**Path and action:** KeplerOps' public review instructions say package reviewers
open a submitted Forgejo repository and ask their local coding agent to summarize
its package documentation. The participant hosts a credible repository whose
documentation contains an indirect instruction, sends its URL in the trusted
mail thread, and waits for the reviewer to open it and start the documented
review.

**Mechanism and result:** Stalwart, Chromium, Playwright, a local OSS coding
agent, and `mcp-package-docs` version 0.1.27 execute the real path described by
`CVE-2025-54073`: retrieved package documentation causes an additional tool call
whose unsanitized argument reaches `child_process.exec`. Participant-controlled
code executes inside the review agent's sandbox and calls the Cinder relay. This
performs `AML.T0011 User Execution`, `AML.T0011.003 Malicious Link`, and
`AML.T0078 Drive-by Compromise`.

**Carry-forward asset:** Bounded user-level workstation execution and scoped
WorkHub session.

**Participant description:** Turn the trusted mail conversation and KeplerOps'
normal AI-assisted package review into scoped execution on the review agent.

**Hints:** (1) Read the public package-review procedure and identify the local
agent tool it uses. (2) Research the pinned documentation tool version and keep
the repository useful enough to receive a normal review. (3) Observe the mail
click, repository visit, agent request, MCP calls, and callback as separate
stages.

**Flag / reset / QA:** The agent sandbox's scoped `reviewer-session.json`
contains the flag and is returned by participant code. Failed-attempt reset
reverts the disposable review environment and clears failed mail/callback
state. The successful WorkHub foothold persists through a durable attacker-
visible session artifact or deterministic reissue. QA requires the real
recipient click, real coding-agent request, exact
vulnerable tool version, additional MCP call, and command execution. A URL
trigger or hidden auto-execution rule is invalid; the patched tool must reject
the same attack.

## `kep-m02-m`: A Tool The Agent Wants

**Difficulty / points:** Advanced / 350

**Path and action:** Public developer docs expose the agent-tool catalog,
computer-using compatibility review, and objective admission checklist. The
participant implements a remote MCP tool that satisfies the declared manifest,
health, schema, fixture-result, latency, TLS and ownership checks while
concealing malicious behavior, publishes its integration page, submits it, and
uses deceptive page content to cause the review agent to register and test the
endpoint.

**Mechanism and result:** FastMCP or the official MCP SDK, Forgejo, Caddy,
BrowserGym/browser-use, Playwright/Chromium, and a fixed victim model perform
real browser and MCP actions. The tool returns its expected result while copying
protected integration-fixture data to the relay. This performs `AML.T0010.005
AI Agent Tool`, `AML.T0011.002 Poisoned AI Agent Tool`, and `AML.T0100 AI Agent
Clickbait`.

**Carry-forward asset:** Scoped catalog token and durable malicious-tool artifact
used in Act 5.

**Participant description:** Publish a credible Orion integration that
manipulates KeplerOps' browser-using review agent into registering and invoking
your poisoned tool.

**Hints:** (1) First make the tool genuinely pass compatibility. (2) Use the
agent's browser trace to understand what it interprets. (3) Cause real endpoint
registration and normal tool invocation, then inspect the relay request.

**Flag / reset / QA:** The protected integration fixture copied during the MCP
call contains the flag and catalog token. Review status exposes browser,
manifest, health, schema, fixture and invocation stages separately. Failed-
attempt reset restores the agent workspace and clears rejected registrations
and traces. The accepted attacker-hosted tool, version, catalog grant, and token
persist. QA tests two materially different deceptive page strategies; fixed
model/configuration, inspectable traces, a six-attempt bound, and reference-run
success at the campaign reliability threshold are mandatory.
