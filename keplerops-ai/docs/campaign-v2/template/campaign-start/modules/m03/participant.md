# Module 03 - Cinder Typhoon Operator Guide

You are operating inside the realistic KeplerOps enterprise as a Cinder Typhoon
field operator. Module 03 turns access from the earlier acts into agent,
retrieval, and supply-chain effects against Orion release operations.

Work only through surfaces your operation has earned: Cinder Forgejo, KeplerOps
Forgejo, devpi, Verdaccio, WorkHub, Orion Assistant, Airflow review queues,
Cinder object storage, Cinder notebook, Qdrant read paths, the Cinder registrar,
and the Cinder relay. Keep exact URLs, issue numbers, package versions, registry
integrities, source revisions, object keys, request IDs, and run IDs. A local
note is useful only when the KeplerOps or Cinder system can reacquire the same
native record.

## kep-m03-a - The Helpful Evaluation Update

**Objective:** Turn a trusted evaluation dependency into worker access while
leaving its advertised scoring behavior intact.

**Start:** Open the KeplerOps evaluation worker repository and read the locked
`orion-eval-utils` source and dependency-update runbook. Keep the Cinder package
publisher path from the partner package work.

**Method:** Publish a higher exact `orion-eval-utils` version from the same
stable index. Preserve `score_batch(inputs)` byte-for-byte in behavior. Add
import-time diagnostics that activate only inside the worker when the documented
callback and mounted worker reference are present. Request the normal evaluation
dependency review for your new exact version and wait for the clean worker run.

**Outcome:** The worker completes its normal score, installs your exact artifact,
and writes a relay-backed native record joining package version, artifact digest,
score digest, callback digest, and worker run.

**Progressive hints**

1. The lockfile tells you the index and exact baseline version.
2. The update must preserve the public score fixture before any diagnostic
   behavior matters.
3. The worker-owned run is the important environment; Kali imports and
   self-sent relay traffic are noise.
